# Аудит SQLite в music-manager

22 ноября 2026 · рабочее дерево `bd-issues` на базе `41c3f99`, включая незакоммиченные миграции 7–12 · SQLite приложения 3.53.4.

**База физически цела. Наиболее существенные ошибки возникают при сопоставлении записей.** После замены MP3 на том же пути SQLite может сохранить ISRC прежней записи и подтвердить наличие отсутствующей песни. Загрузчик может пропустить песню другого исполнителя. API Радара использует поле `artist_id` для двух разных ключей, что позволяет записать настройки каталога другому артисту. Эти три результата получены на временных базах через методы приложения. В локальной медиатеке соответствующих случаев не обнаружено.

Проверены создание базы с нуля, обновление локального снимка, повторное открытие v12, обновление отдельной v6, связи, индексы, планы запросов и сканирование без обращения к каталогам. Продакшен, объёмы серверных данных и время миграции на них в выборку не входят.

Нет повторов ключа «исполнитель, название, тип» и одинаковых конкретных Deezer ID у разных карточек. У 117 из 238 строк кредитов нет локального `artist_id`. Для них не найдено буквального совпадения имени в локальной таблице. Схема допускает участников внешнего каталога, у которых ещё нет локального артиста.

До скана таблица замечаний была пуста. Очередь загрузок, история проверок цензуры и OAuth в этом наборе пусты. Их содержимое проверялось на фикстурах и по коду.

## Дефекты, воспроизведённые на отдельных базах

P1 означает ошибочное изменение пользовательских данных или результата основной операции. P2 означает неверную выдачу, устаревшие данные или неполную диагностику.

## Модель данных и дублирование полей

Все 22 таблицы актуальной схемы перечислены ниже. В SQLite объявлены 17 внешних ключей. Связи, заданные путями, JSON или полиморфным идентификатором, в это число не входят.

| Таблицы | Связи, владелец и смысл хранения |
|---|---|
| `artists`, `tracked_artists` | Локальная идентичность и отдельные настройки поиска в каталогах. FK из настроек допускает NULL для старых внешних записей и запрещает удаление связанного артиста. Имя, нормализованное имя, Deezer/Yandex ID встречаются в обеих таблицах. Для Deezer Радар предпочитает пользовательскую настройку, сканер альбомов читает ID локального артиста. Это два значения с разной семантикой; их следует явно назвать и показывать, какое используется. Несколько строк старых настроек одного артиста допустимы при миграции. Не вводить UNIQUE без правила выбора и сохранения пользовательских данных. |
| `albums`, `album_artists`, `tracks` | Локальный альбом уникален по корню папки, трек — по пути. У трека свой основной артист, у альбома — основной артист, текст TPE2 и упорядоченные участники. Эти роли могут различаться даже у одного файла. Ключи таблицы участников защищают от повторения артиста и позиции в одном альбоме. Из TPE1 в индекс попадает только основной артист. Для поиска гостей трека нужна отдельная связь с порядком; добавлять гостей в `album_artists` неправильно. |
| `genres`, `track_genres` | Связь M:N, уникальна пара трек/жанр. Имя из тега и каноническое имя нужны аудиту вариантов. Повторная индексация одного файла заменяет его связи в транзакции. |
| `release_tracklist` | Ожидаемая позиция уникальна по альбому, диску и номеру. `artist_id` ссылается на исполнителя, `artist_credit` сохраняет полную подпись каталога. `is_present`, `albums.is_complete`, `present_tracks_count` и `expected_tracks_count` — производные. Штатная сверка обновляет их вместе. У локального трека допускаются неизвестная позиция и несколько файлов на позиции, поэтому безусловная уникальность на `tracks(album_id,disc_number,track_number)` потеряет информацию. |
| `radar_releases`, `radar_release_sources`, `radar_release_artists` | Карточка содержит статус пользователя и выбранное представление. У источника собственные заголовок, артист, URL, внешний ID и треклист. MusicBrainz release group может объединять несколько конкретных изданий. Карточка дополнительно хранит идентификаторы провайдеров и JSON-треклист. Закрепить, какие поля вычисляются из источников, и проверять согласованность при смене или удалении источника. Глобальный UNIQUE по всем парам «провайдер, ID» сломает связь нескольких изданий с одной группой. |
| `download_jobs`, `app_settings` | Статус, прогресс и очередь нужны для SQL-выборки. `selection_json` сохраняет снимок выбора, `backfill_selection` — конкретные позиции докачки, `artist_name` — подпись в момент создания, nullable FK — связь с локальной идентичностью. Параллельные представления требуют проверки на повторе и восстановлении. В v12 снимок и состояние задачи основной репозиторий сохраняет одной транзакцией. Настройки и OAuth из ID3 восстановить невозможно; миграция v9 объединяет прежние наборы ключей OAuth. |
| `audit_issues`, `library_artist_conflicts`, `library_index_pending` | Текущие замечания, конфликт идентичности для файла и журнал ещё не согласованных изменений ФС. `audit_issues(entity_type,entity_id)` — программная ссылка без FK. Индекс ускоряет поиск, но не защищает от осиротевших строк. Для журнала путь нужен ещё до появления целевого трека. Для конфликта ссылка на выбранного артиста допускает SET NULL. |
| `censorship_runs`, `censorship_items`, `censorship_evidence_archive` | Запуск → элементы → архив расхождений старых доказательств. Исходный и текущий пути сохраняют историю перемещения. Хэш проанализированного аудио и хэш на момент ручного решения нужны для проверки применимости вердикта. Удаление этих «дублей» лишило бы решение контекста. В v12 рабочие доказательства находятся в `result_json`; архив сохраняет старые несовпадающие представления. |
| `censorship_cache`, `censorship_transcripts`, `censorship_cloud_usage` | Повторно используемый результат, расшифровка и расход по провайдеру и дню UTC имеют разный жизненный цикл. Очистка устаревших результатов затрагивает первый кэш; квота резервируется атомарно. Эти таблицы нельзя очищать вместе с перестраиваемым индексом медиатеки. |

**Поля, которые стоит пересмотреть.** Поиск по актуальным читателям и писателям показал, что `tracked_artists.is_followed`, `tracked_artists.auto_download` и `radar_releases.auto_download_enqueued_at` пережили удаление подписок и автозагрузки. Вместе с ними остался индекс `idx_tracked_artists_followed`. У `tracks.lyrics_path` не найдено поддерживающей записи сканером: фактический sidecar определяется по базовому имени и расширению. Удаление таких колонок стоит оформить новой миграцией после проверки старых клиентов. **Другие производные с риском расхождения.** `has_embedded_cover` описывает файл, а `albums.has_cover` читается также аудитом альбомов. При индексации применяется максимум прежнего значения и нового. После внешнего удаления последней встроенной обложки обычная переиндексация сама по себе не сбросит флаг альбома. При исправлении нужно учитывать также обложку в папке. `tracks.file_hash` — сокращённый SHA-256 **пути**. Его можно использовать для поиска пути, но он ничего не доказывает о совпадении аудио. Массовая очистка дубликатов сейчас отдельно сравнивает SHA-256 целых файлов и защищает файлы текстов от конфликтов. ## Дублирование прикладной логики

- Выдача ленты, число непрочитанных и смена статуса релиза реализованы и в общем пакете БД, и в SQLite-репозитории Радара. В обоих местах UPDATE возвращает успех при отсутствии ID. Проверено на ID 999999 через репозиторий модуля. Возврат ошибки при нуле изменённых строк и одна общая реализация устранят риск расхождения двух API. Образец общей реализации уже есть в запросе дискографии. [Общий пакет](../../../internal/db/radar_releases.go#L273) · [репозиторий](../../../internal/features/radar/repository.go#L143)
- Поиск медиатеки отдельно реализован для общего пакета, файлового менеджера и аудита. Все три собирают запросы по трекам, альбомам и артистам. В общем пакете, например, ошибки SELECT и Scan могут превратиться в пустую или укороченную выдачу. Вынести общую выборку и обработку ошибок, оставив отдельными форматы ответов и действительно различающиеся фильтры. [Общий поиск](../../../internal/db/queries.go#L180) · [файловый менеджер](../../../internal/features/filemanager/repository.go#L298) · [аудит](../../../internal/features/audit/repository.go#L147)
- Для очереди существуют два метода SaveJob. Метод общего пакета обновляет только скалярные поля, основной модуль downloader — также JSON-снимок выбора. При работе старого писателя с такой строкой выбор останется от прежнего состояния. Это риск повторного использования старого API. В штатном пути создания задач используется сервис downloader; сбой в нём по этой причине не установлен. [Старый писатель](../../../internal/db/queries.go#L36) · [сохранение снимка](../../../internal/features/downloader/repository.go#L165)

## Миграции, ограничения и стоимость запросов

- **Одинаковый номер версии не гарантирует одинаковый DDL.** Обе базы v12 имеют 22 таблицы и 11 триггеров. На чистой установке 44 явных индекса (63 вместе с автоматическими), после миграции локальной базы — 46 (65 вместе с автоматическими). В мигрированной базе дополнительно есть `idx_tracks_mtime_size`, `idx_audit_issues_unresolved`; одноимённый `idx_tracks_clean` построен по `(clean_title,artist_id)` вместо `(clean_title)`. У старой `tracks.lyrics_status` остался CHECK на допустимые значения, у чистой его нет. Текущий писатель выдаёт допустимые значения. Зафиксировать целевые ограничения и индексы и проверить следующий переход с обеих исторических схем. [Распознавание старых схем](../../../internal/db/migration_001_layout.go) · [Исходный DDL](../../../internal/db/schema.sql)
- **Один точный дубль индекса.** И `idx_tracks_artist`, и `idx_tracks_artist_id` — обычные индексы одного `tracks(artist_id)`, с одинаковой сортировкой и без предиката в обеих базах. Одного достаточно. На Радаре отдельный `(clean_artist_name)` совпадает только с префиксом `(clean_artist_name,status)`. Решение о нём принимать по планам реальных запросов и стоимости записи. [Миграция 1](../../../internal/db/schema.sql) · [Миграция 5](../../../internal/db/migration_005_artist_identity.go)
- **Два обратных поиска по FK сканируют таблицы.** Подтверждено через EXPLAIN QUERY PLAN для `track_genres.genre_id` и `library_artist_conflicts.resolved_artist_id`. Остальные дочерние FK имеют ведущий ключ подходящего индекса или целочисленный PK, в том числе у всех трёх таблиц связей альбомов и Радара. Индекс на жанр имеет смысл измерить на большой медиатеке, а на конфликты — при накоплении таких записей.
- **Поиск подстроки и очередь.** Проверка `instr(search_title,?)>0` дала `SCAN tracks USING COVERING INDEX`, а не точечный поиск. Индекс всё ещё полезен запросам на равенство. FTS-таблиц нет. Получение старейшей задачи использует индекс статуса и `USE TEMP B-TREE FOR ORDER BY`. На длинной очереди стоит проверить индекс `(status,created_at)` с порядком rowid. На трёх треках время ответа не характеризует крупную установку. [Поиск файлов](../../../internal/features/filemanager/repository.go#L298) · [Выдача задачи](../../../internal/features/downloader/repository.go)
- **Миграции и сохранность истории.** Снимок v0 успешно прошёл до v12 и повторно открылся с успешными integrity/FK checks. База, созданная отдельно кодом коммита `41c3f99` с тестовым ручным пином, тоже прошла с v6 до v12. После этого пина в активной схеме больше нет, а в автоматически созданной SQLite-копии v6 он сохранился. Удаление пинов, старой таблицы пропусков и радио предусмотрено планом. У pre-v7 копии из v0 исходная версия также осталась 0. Общий минутный deadline охватывает резервирование и всю цепочку миграций. Время обновления крупной серверной базы не измерялось. [Исполнение и резервирование](../../../internal/db/migrations.go) · [Переход v7](../../../internal/db/migration_007_track_sources.go) · [Удаление радио](../../../internal/db/migration_011_remove_radio.go)
- **Ограничения для JSON и состояний.** В DDL нет общей проверки допустимых статусов задач или валидности JSON-снимков. Загрузчик распознаёт повреждённый снимок и выдаёт ошибку конкретной задачи. У Радара ошибка разбора одного непустого треклиста прерывает общую сверку. Перед ужесточением ограничений следует отдельно диагностировать старые значения и обеспечить доступ к остальным строкам. [Чтение задачи](../../../internal/features/downloader/repository.go) · [Сверка Радара](../../../internal/db/radar_reconcile.go#L286)

## Порядок исправлений и повторная проверка

1. Исправить перенос ISRC и привязки каталога после замены файла или издания. Проверять связку «файл → индекс → комплектность → позиции для докачки».
2. Устранить ложный автопропуск и измерять качество импортированного аудио. Проверять результат как в предпросмотре, так и при выполнении очереди.
3. Привести API Радара и кредиты провайдеров к однозначным ID. Добавить случаи перекрёстных ключей, одноимённых артистов и отозванного кредита.
4. Исправить пересчёт агрегатов, уборку конфликтов и возврат ошибок. Затем унифицировать DDL версионной миграцией. Удалять полные дубли индексов отдельно от изменений поисковой логики.

[Контрольные запросы для v12](checks-v12.sql) проверены на чистой базе, мигрированной копии и копии после сканирования. Выполнять в соединении только для чтения. Для полной `PRAGMA integrity_check` нужен драйвер с зарегистрированной `music_search_key`, которая используется в индексах выражений. SQL-проверки не определяют идентичность аудиозаписей и не заменяют повторение сценариев из таблицы выше.

Полный прогон `go test -count=1 -v ./...` и статическая сборка с `CGO_ENABLED=0` прошли. Штатные тесты и воспроизведённые дефекты совместимы: приведённые комбинации входных данных раскрывают пробелы в покрытии. Рабочая база осталась на версии 0.

## Исправления после аудита

- Текущие ID3-теги заменяют старый ISRC. При изменении идентичности альбома библиотека сохраняет ID папки и сбрасывает прежнюю каталожную привязку. Ответ каталога проверяет ревизию альбома перед записью. Счётчики позиций и наличие обложки пересчитываются из текущих данных.
- Сканер измеряет параметры звукового потока через ffprobe. Контрольный MP3 попал в индекс с 128 кбит/с и длительностью 10,031 с, загрузчик предложил улучшить качество. Добавлены проверки для 128, 320 кбит/с и VBR.
- Проверка наличия трека использует ISRC либо точные нормализованные название и имя однозначно определённого артиста. Несколько кандидатов без точного ISRC требуют выбора. У Радара один библиотечный `artist_id` для чтения, записи и повторного сканирования выбранного артиста. Старый ID настроек принимается при совпадении имени и отсутствии библиотечного ID с этим числом.
- Радар хранит кредиты по источникам и обновляет дискографию по ID провайдера. Сведения группы MusicBrainz хранятся отдельно от параметров конкретного издания. Некорректный старый треклист больше не прерывает проверку остальных карточек.
- Поиск медиатеки и запросы ленты Радара используют общие реализации. Сводка аудита возвращает ошибки SQLite и сканирования. Полный скан убирает конфликты исчезнувших файлов. Старый метод записи очереди защищает задачи со снимком выбора от частичного обновления.
- Миграция v13 убирает дубли индексов, добавляет индексы для обратных связей и старейшей задачи, приводит установленные ограничения на новые значения `lyrics_status` к единому поведению. Исторические поля подписок и пути сохранены. Произвольный поиск подстроки по-прежнему использует `instr`; внедрение FTS изменило бы его семантику.

Копии локальной v0, мигрированной v12 и чистая v13 прошли проверки целостности и внешних ключей. В двух копиях сохранены все 121 карточка и 238 строк кредитов Радара. [Миграция v13](../../../internal/db/migration_013_audit_consistency.go) · [Измерение MP3](../../../internal/id3/audio_probe.go)
