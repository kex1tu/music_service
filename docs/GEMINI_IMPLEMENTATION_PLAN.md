# Задание Gemini: улучшения Music Manager по результатам анализа трёх репозиториев

Подготовлено 9 ноября 2026 года. Этот документ можно передать Gemini целиком.

## Цель

Реализуй полезные улучшения Music Downloader & Tag Manager на основе идей из:

- https://github.com/llistochek/yandex-music-downloader
- https://github.com/R3DCyclops/mp3_PLRKLR
- https://github.com/megapro17/zvukdown

Работай в существующем проекте. Сначала проверь фактическое состояние кода, затем выполняй этапы ниже. Изменения должны проходить через существующие сервисы и очереди. Не выполняй деплой, push, массовую обработку медиатеки и реальные загрузки без отдельного поручения. Коммиты в это задание не входят.

## Важные поправки к исходному анализу

Переданный анализ — источник гипотез, а не проверенная спецификация API.

1. Проверка коротких превью уже существует: `validateDownloadedStreamAudio` в `internal/services/downloader/media_processor.go`. Есть тест с коротким синтетическим аудио в `media_processor_test.go`. Не реализовывай её повторно.
2. Оптимизация обложек уже существует: `internal/id3/cover_optimize.go`, функция `OptimizeCoverForID3`; она вызывается из `internal/id3/writer.go`. Это предмет проверки и точечных дополнений.
3. `internal/services/organizer/path.go` ограничивает компоненты по числу рун. Требуется отдельное ограничение итогового компонента по байтам UTF-8. Особенно важен каталог, собираемый из названия альбома и исполнителя: ограничения отдельных частей недостаточно.
4. `YandexMusicClient.ParseURL` возвращает тип ресурса и `int64`. UUID плейлиста в этот интерфейс не помещается. Нельзя просто добавить ещё один числовой case.
5. `lyrics.LyricsProvider.Search` принимает исполнителя, название, альбом и длительность, но не ID Яндекса. Для точного получения официального текста нужен способ передать идентичность трека.
6. В `AGENTS.md` скачивание закреплено за yt-dlp. Собственная HTTP-загрузка и AES-дешифрование в Go конфликтуют с этим требованием. Прямые потоки выделены в условный этап, а не включены в обязательную реализацию.
7. Не считай доказанными актуальность закрытых API, требования подписок, проценты покрытия текстами, скорость загрузки и оценки «40/150 строк». Проверяй протокол по исходникам и фиксируй ограничения отдельно.
8. Не смешивай ключ подписи запроса и ключ дешифрования конкретного потока. Наличие HMAC и AES-CTR в чужом проекте не определяет автоматически параметры совместимой реализации.

## Этап 0. Зафиксировать исходное состояние

Прочитай `AGENTS.md`, `Architecture.md`, `plan.md`, последние записи `PROGRESS.md` и применимые инструкции навыков. Перед изменением открывай файл, перед вызовом чужого метода проверяй его сигнатуру.

Проверь `git status` и diff. В рабочем дереве уже есть изменения поиска SoundCloud, очереди, фронтенда и деплоя. Сохрани их; не сбрасывай и не перезаписывай. При использовании отдельного worktree учитывай, что незакоммиченные изменения исходного дерева автоматически туда не попадут.

Зафиксируй коммиты сторонних репозиториев, просмотренные файлы и фактические лицензии. Чужие проекты нужны только как справочный материал: не запускай их Python-код и не добавляй их зависимости. Не копируй код с несовместимой или отсутствующей лицензией. При допустимом заимствовании соблюдай требования уведомлений и атрибуции. При неясной лицензии используй собственную реализацию требований и документированного протокола.

В `plan.md` добавь отдельный раздел, сохранив существующие планы. Укажи необходимость изменений в resolver, organizer, lyrics, downloader и, при необходимости, HTTP/UI/DI/DB. При реальном конфликте с инвариантами зафиксируй его в `PROGRESS.md` и останови зависимый этап до прояснения.

**Результат:** короткая матрица «уже есть / требуется / требует проверки / конфликтует», список затрагиваемых файлов и исходные результаты тестов. Не выдавай существующие сбои за результат своих изменений.

## Этап 1. Имена файлов и каталогов по байтам UTF-8 — первый приоритет

Основная область: `internal/services/organizer/`, плюс обнаруженные места формирования имён в downloader.

1. Добавь небольшую функцию усечения по байтовому бюджету с сохранением границ UTF-8. Размести её рядом с логикой формирования имён; не меняй семантику `PathSandbox.Resolve` ради автоматического переименования путей.
2. Сохрани существующие ограничения по числу рун, добавив ограничение итогового компонента по байтам. Не меняй смысл параметра `maxLength` у существующей функции молча.
3. Рассчитывай бюджет для полного имени: номер трека, разделители, название, расширение и возможный суффикс коллизии. Применяй ограничение к итоговому каталогу `{Album} - {Album Artist}`, а не только к его частям.
4. Для текущей Linux-цели используй документированный бюджет компонента не более 255 байт с необходимым резервом. Не утверждай, что это универсальный лимит NTFS или всей длины пути.
5. Обрабатывай пустое имя после очистки, короткий бюджет, длинный fallback, завершающие точки и пробелы. Проверь совместимость с существующими правилами коллизий и дедупликации.
6. Сопутствующие `.lrc`, `.txt` и изображения должны сохранять согласованные имена и перемещаться существующим механизмом companions.

**Приёмка:** длинная кириллица, emoji, ASCII, длинные альбом + артист, границы бюджета, суффиксы коллизий и расширения. Все результаты валидны как UTF-8 и укладываются в бюджет; разные исходники не перезаписываются. Короткие существующие имена сохраняют прежний результат. Создание и перенос тестовых файлов проходят через действующие sandbox/safefs-механизмы.

## Этап 2. Импорт публичных плейлистов Яндекс Музыки

Основная область: `internal/services/resolver/`; HTTP и frontend менять только для полного пользовательского сценария.

1. Проверь актуальные форматы ссылок и ответы API по исходникам. Не предполагай, что `/users/{owner}/playlists/{kind}` и `/playlists/{uuid}` используют один идентификатор или endpoint.
2. Добавь представление ресурса с нужными идентификаторами. Сохрани совместимость существующего `ParseURL` через адаптер либо мигрируй все вызовы с проверками.
3. Поддержи подтверждённые формы публичных URL и iframe. Из iframe извлекай только `src`, проверяй схему и hostname, после чего используй общий URL-парсер. HTML не выполняй и не отображай как доверенный.
4. Нормализуй ввод до общей проверки допустимого URL, иначе iframe будет отклонён раньше resolver. Защити ввод от чрезмерной длины и чужих доменов, включая похожие имена хостов.
5. Запрашивай метаданные через существующий клиент Яндекса с context, таймаутом и proxy. Публичный сценарий должен работать без токена там, где это поддерживает API. Отсутствие доступа к приватному плейлисту показывай как понятную ошибку.
6. Сохраняй порядок и реальные повторения треков. Если очередь требует уникальные ключи элементов, отдели ключ вхождения от каталожного ID трека.
7. Обработай пагинацию, пустой плейлист, удалённые или недоступные треки и частичные ответы. Показывай пропуски; не выдавай неполный результат за полный.
8. У каждого трека сохраняй собственные альбом, исполнителей, обложку, год и номера. Не записывай название плейлиста в альбом всех треков. Сохрани каталожный ID Яндекса для следующего этапа.
9. Передавай результат в существующие предпросмотр, очередь и подбор/выбор аудиоисточника. Импорт метаданных не должен сам скачивать аудио или менять назначенный вручную источник.

**Приёмка:** mock-тесты URL/iframe и обоих типов идентификаторов, старых album/track/artist URL, пагинации, повторов, пропусков, 401/403/404/451/429, отмены контекста, невалидного JSON и чужих доменов. UI: вставка → предпросмотр → очередь без блокировки интерфейса. При изменении UI проверь desktop/mobile и применимые навыки дизайна.

## Этап 3. Официальные тексты Яндекса с fallback

Основная область: resolver + lyrics, интеграция с обоими существующими путями загрузки и DI.

1. Подтверди актуальный протокол получения LRC и необходимые параметры авторизации/подписи. Не реализовывай endpoint по одному предположению из анализа.
2. Используй подтверждённый каталожный ID Яндекса. Не сопоставляй текст с первым результатом нечёткого поиска по названию. Не извлекай Яндекс-ID из TrackID другой платформы.
3. Выбери минимальное совместимое расширение запроса lyrics: необязательная идентичность источника либо отдельный метод точного получения. Сохрани существующие вызовы `SearchLyrics` и внедрение провайдера в тестах. Избегай циклических импортов; зависимости собирай в DI.
4. Если ID нужен после перезапуска очереди, обеспечь его сохранение и восстановление через действующий механизм persistence. Миграцию DB добавляй только при необходимости и с обратной совместимостью.
5. Порядок: подходящий текст Яндекса по точному ID → существующая цепочка провайдеров. Проверь фактический состав цепочки; не добавляй заново провайдеры только потому, что они упомянуты в отчёте.
6. Отсутствие токена, текста, доступности API или поддержки LRC не должно срывать загрузку музыки. Отмену пользовательского контекста соблюдай; не продолжай fallback после отмены. Исключи бесконечные повторы и утечку токенов в логи/ошибки.
7. Проверяй, что ответ содержит текст, а не HTML/JSON ошибки. Ограничивай размер ответа и время получения. При перенаправлении на URL текста не передавай OAuth-заголовок чужому хосту.
8. Синхронизированный текст сохраняй в `.lrc`, обычный — в `.txt`, только через sandbox/safefs и существующую организацию staging. Пользовательский текст не перезаписывай молча. В ID3 не добавляй USLT/SYLT.

**Приёмка:** mock-тесты точного ID, отсутствия ID/токена, синхронизированного и обычного текста, пустого/повреждённого ответа, ошибок, таймаута, отмены и fallback. Проверка текста после переноса organizer и после восстановления задания. Поиск текста не пишет файлы; сохранение выполняется существующим явным действием/пайплайном.

## Этап 4. Проверить уже реализованные превью и обложки

### Превью

Проверь использование `downloadAndValidateRawStream` всеми путями загрузки, включая смену версии. Сохрани правило «фактическая длительность <35 секунд при ожидаемой >60 секунд» как эвристику превью, а не доказательство региональной блокировки или цензуры.

Проверь короткие легитимные треки, неизвестную длительность, границы порогов и ошибку ffprobe. Дополняй код и тесты только при найденном пробеле. Не меняй автоматически выбранный пользователем источник.

### Обложки

Используй `OptimizeCoverForID3`. Проверь покрытие путей записи APIC, лимит сетевого ответа, размеры изображения до полного декодирования и поведение при ошибке. Уменьшение до 1000 px само по себе не гарантирует жёсткого лимита байтов; при необходимости добавь ограничение результата в существующий механизм.

Получение оригинальной обложки через `orig` рассматривай как дополнение после проверки поддержки. Обеспечь fallback на текущую ссылку 1000×1000; ошибки обложки не должны срывать аудио. Сохранение оригинала отдельным файлом вводи только при необходимости существующего сценария, без pingo/ImageMagick и других новых runtime-зависимостей.

**Приёмка:** целевые регрессии для найденных пробелов; JPEG/PNG, повреждённый и чрезмерно большой вход, валидный APIC и MIME. Не объявляй существующие функции новой реализацией.

## Этап 5. Прямой источник Яндекса — условный, после архитектурного решения

Сначала подготовь техническую записку. Обязательные этапы 1–4 не должны зависеть от её реализации.

- Проверь, способен ли используемый standalone yt-dlp работать с нужным источником Яндекса в рамках текущих правил. Метаданные через Go-клиент и скачивание аудио — разные операции.
- Если требуется собственная HTTP-загрузка и AES-дешифрование в Go, зафиксируй противоречие с `AGENTS.md`, раздел 2, пункт 4. Не реализовывай обход и не меняй инвариант самостоятельно. Для этого пути требуется отдельное явное изменение архитектурных требований.
- До решения не расширяй whitelist произвольными CDN и не передавай неподтверждённые потоки в очередь.

После отдельного разрешения зависимого пути потребуется самостоятельная спецификация: точная идентичность трека, временные URL, ключ и IV/счётчик AES-CTR, HMAC-параметры, авторизация, proxy, лимиты, отмена, staging и отсутствие секретов в логах/DB. Самостоятельный crypto-клиент без подтверждённого протокола неприемлем.

Любой разрешённый источник должен завершаться штатным ffmpeg → MP3 320 kbps CBR / 44.1 kHz → внутренний ID3v2.4. Не включай автоматическую замену выбранного пользователем источника на SoundCloud/YouTube при ошибке Яндекса. Частичные файлы не должны получать статус ready.

## Не включать в эту реализацию

- Парсеры Hitmo/Lmusic, новые поисковые цепочки и повторную реализацию существующего matcher.
- Интеграцию Звука на предположении, что API 2021 года актуален или отключён: его состояние здесь не подтверждено. Возможное исследование — отдельная задача.
- Перенос Python/Tkinter/Mutagen, добавление Node/npm, Docker или новых внешних инструментов обработки изображений.
- Вшивание текстов, смену формата выходного аудио, автоматическую перезапись медиатеки и утверждения о гарантированном отсутствии цензуры.

## Общие критерии готовности

1. Все файловые операции используют `PathSandbox.Resolve` и существующие защищённые safefs/mediaexec-механизмы. Не упрощай их до открытия ранее проверенного строкового пути.
2. Аудио до подтверждения остаётся в `tmp_downloads/{job_id}/`; перенос в медиатеку выполняет organizer.
3. Секреты остаются в окружении. Новые настройки, если действительно нужны, отражены в `.env.example` без реальных значений.
4. Контракты API и документация обновлены при изменении интерфейсов. Старые сохранённые задания и клиенты продолжают работать.
5. Внешние HTTP-запросы во всех автоматических тестах замоканы. Реальные сетевые проверки не подменяют тесты и не запускаются как часть suite.
6. Выполнены проверки из корня проекта:

   ```bash
   go test -v ./...
   go test -race -p 1 ./...
   go vet ./...
   CGO_ENABLED=0 go build -ldflags="-s -w" -o bin/music-manager cmd/server/main.go
   git diff --check
   ```

   Последовательный race-прогон выбран с учётом отмеченных в `PROGRESS.md` временных бюджетов SQLite-тестов. Не ослабляй тесты ради зелёного результата. Если проверка заблокирована средой, укажи команду, ошибку и непроверенное поведение.

7. Обновлены `plan.md` и `PROGRESS.md`: отдельно реализованное, проверенное mock-тестами, проверенное реальной интеграцией и заблокированное. Успешные mock-тесты не доказывают доступность приватного API в production.

## Порядок работы и итоговый отчёт

Выполняй этапы последовательно: исходное состояние → UTF-8 имена → плейлисты → тексты → точечные дополнения превью/обложек → записка по прямому источнику.

Доведи независимые этапы до готовности, даже если отдельный внешний протокол не удалось подтвердить. Для неподтверждённого этапа оставь точное описание блокировки; не создавай фиктивную работающую интеграцию.

В финальном отчёте укажи:

- что реализовано и где;
- что уже существовало и было только проверено;
- какие идеи использованы из каждого репозитория и на каких условиях;
- команды проверок и фактические результаты;
- неподтверждённые внешние API и оставшиеся ограничения;
- отдельно: статус прямого источника Яндекса и требуемое архитектурное решение.

Не выполняй самопроверку рекурсивным делегированием этой же задачи самому себе через agy.
