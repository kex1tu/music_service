# Исследование способов загрузки аудио помимо yt-dlp

**Дата исследования:** 10 ноября 2026 года
**Статус:** Исследовательская записка и архитектурный эскиз интеграции (код и правила проекта не изменялись)
**Контекст проекта:** Pure Go (Chi), SQLite WAL, Linux/systemd, no-build SPA (HTML5 + Tailwind CDN + Alpine.js CDN).
**Текущий инвариант (AGENTS.md §2.4):** «Аудио-пайплайн фиксирован. Скачивание — `yt-dlp`; конвертация — `ffmpeg` в MP3 320 kbps CBR / 44.1 kHz; теги — строго ID3v2.4 UTF-8 через внутренний пакет `internal/id3`...»

---

## 1. Краткий ответ

### 1.1. Какие методы получения аудио существуют в индустрии
1. **Универсальные CLI/скриптовые экстракторы-оркестраторы** (`yt-dlp`, `streamlink`): инкапсулируют решение JavaScript-челленджей (EJS/n-sig), разбор сложных веб-манифестов и оркестрацию внешних транспортов.
2. **Прямой HTTP(S) транспорт на Go** (`net/http`): скачивание файлов по статическим или криптографически подписанным CDN-ссылкам с поддержкой Range-запросов, resume и параллельных чанков.
3. **Сегментные HLS/DASH загрузчики** (Go-парсеры m3u8/mpd + пул HTTP-воркеров либо вызов `ffmpeg` в режиме демультиплексора): сборка незащищенных потоков или потоков со стандартным AES-128 шифрованием по открытому ключу манифеста.
4. **Специализированные сервис-адаптеры (Reverse-Engineered API)**: прямое взаимодействие с приватными REST API стримингов (SoundCloud API v2, Яндекс Музыка API с клиентской HMAC-подписью современного API и дешифрованием AES-CTR).
5. **Одноранговые P2P-сети (BitTorrent, Soulseek)**: децентрализованный поиск и скачивание аудиоматериалов (swarm-протоколы, очереди пиров, DHT).
6. **Локальный импорт и пользовательская загрузка**: HTTP multipart-upload через веб-интерфейс сервиса либо сканирование каталога горячего импорта (`watch_folder`) без внешних экстракторов.

### 1.2. Что уже делает проект (верифицировано по кодовой базе на 10.11.2026)
- **Каталоги и идентификация:** Разделены каталожные метаданные и физические аудиоисточники. `SourceResolver` (`internal/services/resolver/resolver.go`) агрегирует каталоги Deezer (`client_deezer.go`), Яндекс Музыки (`client_yandex.go`), iTunes (`client_itunes.go`) и YouTube Music (`client_ytmusic.go`). Наличие трека в каталоге не означает получение аудио от этого же провайдера.
- **Выбор источника (Audio Matching):** Действует архитектурный принцип ручного выбора источника пользователем из общей выдачи (`AudioSourceURL`). Автоматическая скрытая подмена одного источника другим при сбое запрещена (`pipeline.go` L383-404, `service.go` L1186-1194).
- **Прямой BitTorrent:** В `resolver_torrent.go` реализовано только сопоставление имени релиза (`dn` из magnet-ссылки) с каталогом Deezer. Реальный транспорт BitTorrent отсутствует; при отсутствии совпадения возвращается явная ошибка (`"прямая загрузка BitTorrent (.torrent/magnet) временно недоступна"`).
- **Транспорт аудио:** Все скачивание замкнуто на `downloadRawStream` (`media_processor.go` L26, `service.go` L1339), вызывающий бинарник `yt-dlp` через обертку `mediaexec.CommandContext`.
- **Изоляция и валидация среды:** В `internal/core/mediaexec/runtime.go` действует проверка: `yt-dlp` обязан быть скомпилированным standalone ELF-бинарником Linux (не Python-скриптом), а в системе должен присутствовать рантайм `deno >= 2.3` для выполнения YouTube EJS. Запуск дочерних процессов изолирован через дескрипторы `/proc/self/fd/*` (`mediaexec/command.go`).
- **Контроль качества:** Выполняется отсечение 30-секундных гео-сниппетов через `ffprobe` (`media_processor.go` L200) и расчет спектральной телеметрии (`aspectralstats`, срез частот rolloff). Постпроцессинг строго фиксирован: `ffmpeg` -> MP3 320 kbps CBR / 44.1 kHz -> нативный `internal/id3` (ID3v2.4 UTF-8, null-разделители) -> staging `tmp_downloads/{job_id}/` -> `organizer.Service`.

### 1.3. Приоритетные направления (Top-3)
1. **Направление 1 (Фундамент): Сохранение и укрепление yt-dlp как основного универсального загрузчика.** Ни одна независимая библиотека на Go или C не успевает за непрерывными изменениями антибот-защиты YouTube и SoundCloud (n-sig, EJS, PO-tokens). Попытка полной замены yt-dlp приведет к деградации сервиса. Приоритет — автоматизация обновления standalone ELF-бинарника, изоляция сессий и ротация сетевых путей.
2. **Направление 2 (Go-нативный резерв): Внедрение нативного Go HTTP/HLS транспорта для открытых и подписанных источников (SoundCloud v2 HLS + прямой Яндекс.Музыка).** Позволяет скачивать аудио с SoundCloud (HLS AAC 160 kbps) и Яндекс Музыки (прямой MP3/FLAC) силами внутреннего Go-клиента без накладных расходов на fork/exec Python/yt-dlp. Это снижает потребление RAM/CPU и дает реальную технологическую независимость для двух ключевых платформ.
3. **Направление 3 (User Fallback): Веб-импорт пользовательских файлов (Direct Upload / Local Staging).** Предоставление пользователю возможности загрузить файл напрямую через браузер (drag & drop в модальное окно) для прогона через штатный пайплайн тегирования и каталогизации. Это гарантированно решает задачу, когда трек отсутствует во всех стримингах или заблокирован правообладателями.

## 2. Матрица сравнения методов и кандидатов

### 2.1. Четыре уровня конвейера загрузки
Для корректного сопоставления каждый метод классифицируется по покрываемым уровням:
- **Уровень 1 (L1 — Catalog / Identity):** Поиск треков, получение ISRC, треклистов, обложек и канонической длительности.
- **Уровень 2 (L2 — Extraction / Auth):** Разрешение публичной страницы в защищенный media URL / манифест (обход бот-челленджей, расчет подписей, авторизация).
- **Уровень 3 (L3 — Transport):** Выкачивание сырых аудиобайтов по протоколам HTTP/HLS/DASH/P2P на диск в staging.
- **Уровень 4 (L4 — Post-processing):** Валидация аудио, декодирование, транскодирование в MP3 320k, запись ID3v2.4 тегов.

### 2.3. Явно исключённые кандидаты и обоснование причин

1. **Spotify (прямое скачивание аудиочерез librespot / spotdl):**
   - *Причина исключения:* Spotify использует DRM Widevine и проприетарное шифрование Shannon/PlayReady для всех аудиопотоков (OGG Vorbis 96–320 kbps и AAC). Утилиты вроде `spotdl` **не скачивают из Spotify**, а лишь считывают метаданные и ищут совпадения на YouTube (подменяя источник). Библиотеки на Rust/C (`librespot`) требуют учетную запись Spotify Premium, эмулируют официальный клиент и систематически банятся антифрод-системами Spotify с перманентной блокировкой аккаунтов. Внедрение прямого стриминга Spotify нарушает законы об обходе DRM и несовместимо с pure Go архитектурой.
2. **Apple Music:**
   - *Причина исключения:* Все полноразмерные потоки Apple Music защищены DRM FairPlay. Публичный доступ ограничен 30-секундными AAC-сниппетами. Прямая загрузка без взлома DRM технически невозможна.
3. **Deezer HiFi / FLAC (дешифрование Blowfish через deemix/streamrip):**
   - *Причина исключения:* В 2021–2023 гг. Deezer закрыл бесплатные ключи шифрования и свободную раздачу FLAC/320k. Публичный API отдает строго 30-секундный превью (что уже отслеживается в проекте через `media_processor.go` L227). Загрузка полного трека требует платной сессионной cookie (`ARL`) и статического мастер-ключа Blowfish. В 2024–2026 гг. Deezer планомерно переводит HiFi-потоки на Widevine DRM, блокируя headless-клиенты. Использование неофициального Blowfish-дешифратора недолговечно и влечет блокировки ARL.
4. **Tidal / Qobuz CLI-рипперы (`tidal-dl`, `qobuz-dl`):**
   - *Причина исключения:* Написаны на Python, требуют учетных записей с активной платной подпиской HiFi Plus, подвержены регулярным отзывам Client ID/Secret и не предоставляют Go-библиотек.
5. **Обертки над yt-dlp (`Zibbp/eos`, `metube`, `tubearchivist`):**
   - *Причина исключения:* Это готовые веб-интерфейсы или каталогизаторы, внутри которых вызывается ровно тот же `yt-dlp`. Они не предоставляют альтернативного бэкенда и не решают задачу независимого резервирования.
6. **Soulseek (`slskd` / `nicotine+`):**
   - *Причина исключения:* Сеть Soulseek ориентирована на интерактивный десктопный обмен: треки скачиваются из очередей конкретных пользователей, скорость отдачи может составлять 10–50 КБ/с, пиры могут отключаться посреди трека или требовать ответного расшаривания гигабайтов музыки. Внешний демон `slskd` требует рантайм .NET 8 / Docker (прямое нарушение AGENTS.md §2.1 и §2.3), а существующие Go-библиотеки (`spotseek`) заброшены и нестабильны.

## 3. Детальный разбор 3 лучших вариантов

### Вариант 1: Укрепленный и оптимизированный yt-dlp (Hardened Standalone ELF)

Текущий базовый инструмент, используемый проектом. Анализ кода (`media_processor.go`, `mediaexec/runtime.go`) показал, что проект уже задействует продвинутые механизмы: запрет Python-скрипта в пользу ELF-бинарника, проверка наличия Deno >= 2.3 для YouTube EJS, маппинг cookies и изоляция дескрипторов.

#### Возможности и ограничения
- **Специфика автономного бинарника:** Официальный `yt-dlp_linux` скомпилирован через PyInstaller. Внутри него находится сжатый образ CPython и базовых библиотек. При старте бинарник распаковывает модули во временную память (`/tmp/_MEIxxxxxx`). Это не нарушает запрет «Zero-Python в runtime проекта», так как бинарник самодостаточен и не требует установленного в OS системного Python.
- **YouTube EJS и Deno:** Современный YouTube требует вычисления параметров сигнатур `n-sig` через исполнение обфусцированного JavaScript-кода плеера (`base.js`). Раньше yt-dlp использовал встроенные регулярные выражения, но Google ускорил мутацию кода. Наличие Deno позволяет yt-dlp безошибочно исполнять JS-челленджи без троттлинга скорости до 40 КБ/с.
- **Внешний загрузчик (aria2c):** Флаг `--downloader aria2c` ускоряет скачивание тяжелых многосегментных файлов за счет многопоточности. Однако для аудио (размер 5–15 МБ) накладные расходы на запуск отдельного процесса `aria2c` нивелируют выигрыш. Для HLS-потоков SoundCloud `aria2c` часто приводит к ошибкам лимита соединений.

#### Оценка надежности и безопасности
- **Авторизация и Cookies:** Поддерживается формат Netscape cookies. Проект уже реализует безопасный fallback: если yt-dlp бракует файл cookies, происходит повторная попытка в гостевом режиме (`media_processor.go` L76-109).
- **SSRF:** yt-dlp принимает целевой URL. В проекте действует жесткий `IsAllowedURL` (`resolver.go` L25-42), отсекающий посторонние домены до вызова процесса.
- **Файловая безопасность:** Использование флагов `--no-download-archive`, `--no-playlist`, а также передача каталога назначения через cwd/ExtraFiles в `mediaexec` гарантируют, что имя файла из тегов YouTube не выйдет за пределы `tmp_downloads/{job_id}/raw/`.

### Вариант 2: Нативный Go HTTP/HLS транспорт (SoundCloud API v2 + Яндекс.Музыка Direct)

Это ключевой независимый кандидат, способный перенять на себя 80%+ нагрузки по аудиопотокам, исключив вызовы тяжелого внешнего процесса yt-dlp.

#### Архитектура компонентов
1. **SoundCloud v2 HLS Client:**
   - *Получение манифеста:* Запрос к `https://api-v2.soundcloud.com/tracks/{track_urn}?client_id={client_id}`.
   - *Извлечение потока:* Парсинг объекта `media.transcodings`. Приоритет отдается протоколу `hls` с mime-type `audio/mp4` (AAC 160 kbps) либо `audio/mpeg` (MP3 128 kbps).
   - *Транспорт сегментов:* Загрузка master `.m3u8` -> загрузка media playlist -> параллельное (2–4 воркера) скачивание чанков `.mp3`/`.aac` через `net/http` с конкатенацией в файл staging.
2. **Яндекс Музыка Direct Client (Legacy Signed MP3 + Modern AES-CTR):**
   - *Схема подписи MP3:* Запрос к `/tracks/{id}/download-info` -> получение XML/JSON с параметрами `host`, `path`, `ts`, `s`. Вычисление MD5-хэша:
     $$\text{sign} = \text{MD5}(\text{Salt} + \text{path}[1:] + \text{s})$$
     Формирование прямого URL: `https://{host}/get-mp3/{sign}/{ts}/{path}`. Скачивание — стандартный HTTP GET с Range-поддержкой.
   - *Схема Lossless FLAC ("encraw"):* Запрос `/get-file-info` -> получение stream URL и 16-байтного ключа `key`. Аудиопоток `flac-mp4` шифруется алгоритмом **AES-128 в режиме CTR** (Counter) с nonce из 12 нулевых байт. Нативный Go-пакет `crypto/cipher` выполняет потоковую расшифровку на лету без промежуточной записи зашифрованного файла на диск:
     ```go
     block, _ := aes.NewCipher(key)
     stream := cipher.NewCTR(block, iv) // 16 bytes: 12 zero bytes nonce + 4 bytes counter
     stream.XORKeyStream(decryptedChunk, encryptedChunk)
     ```

#### Глубокий аудит безопасности (SSRF, Timeouts, Sandbox)
- **Защита от SSRF (Критично):** Простой проверки входного домена недостаточно, так как манифест `.m3u8` или редирект с CDN может указывать на адреса локальной сети (`127.0.0.1`, `10.0.0.0/8`, `169.254.169.254` AWS/cloud metadata).
  *Обязательное решение в Go:* Настройка `http.Transport` с кастомным `DialContext`, проверяющим разрешенный IP-адрес после DNS-резолвинга перед открытием TCP-сокета:
  ```go
  // Проверка каждого сокета на запрещенные диапазоны (RFC 1918, RFC 3927, Loopback, IPv6 ULA)
  Control: func(network, address string, c syscall.RawConn) error {
      // Блокировка приватных и локальных IP
  }
  ```
- **Защита от DNS Rebinding:** IP проверяется непосредственно в хуке `Control` перед установкой соединения, а не предварительным `net.LookupIP`.
- **Изоляция секретов:** Токены авторизации и подписанные временные URL (`sign=...`) должны автоматически вырезаться из логов Chi и не попадать в таблицу `download_jobs`.
- **Staging и PathSandbox:** Файлы пишутся через дескриптор `safefs.Create` непосредственно в `tmp_downloads/{job_id}/raw/01.raw`.

### Вариант 3: Прямой пользовательский веб-импорт (User Web Upload & Watch Folder)

Метод не заменяет стриминги, но закрывает сценарии, где бессильны любые парсеры: покупка на Bandcamp, эксклюзивы на CD/винили, удаленные из сети треки.

#### Архитектура и механика
1. **API Endpoint:** `POST /api/upload` (защищен CSRF и сессионным HMAC-cookie).
2. **Потоковый прием:** Использование `http.MaxBytesReader` (лимит, например, 200 МБ на файл) и `multipart.Reader` для потоковой записи во временный файл через `safefs.Create` без удержания всего файла в оперативной памяти.
3. **Автоматическая идентификация:**
   - Определение формата через сигнатуры первых 512 байт (`http.DetectContentType`) и запуск `ffprobe` через `mediaexec`.
   - Чтение существующих встроенных ID3v2/VorbisComment тегов через `internal/id3.Reader`.
   - Если теги присутствуют — предзаполнение карточки трека в UI; если отсутствуют — запуск матчера по названию файла.
4. **Бесшовный вход в конвейер:** Загруженный файл сразу помещается в `tmp_downloads/{job_id}/raw/01.raw` и передается в штатный `transcodeToMP3` -> `id3.Writer` -> `organizer`.

## 4. Рекомендация по роли yt-dlp

### 4.1. Анализ трех стратегий

1. **Стратегия А: Полная замена yt-dlp на pure Go решения.**
   - *Вердикт:* **Категорически не рекомендуется.**
   - *Аргументация:* Платформы уровня YouTube ведут непрерывную войну со сторонними клиентами. Поддержка собственного реверс-инжиниринга JS-плеера YouTube силами проекта нереализуема. Существующие независимые Go-библиотеки (`kkdai/youtube` и др.) регулярно ломаются и забрасываются авторами. Отказ от yt-dlp уничтожит ключевую функциональность сервиса.
2. **Стратегия Б: Сохранение текущего статуса-кво (yt-dlp как безальтернативный монопольный загрузчик).**
   - *Вердикт:* **Приемлемо, но неоптимально.**
   - *Аргументация:* Оставляет систему уязвимой при локальных сбоях yt-dlp (например, при задержке обновления upstream или поломке конкретного экстрактора) и создает лишние накладные расходы при скачивании с простых сервисов вроде SoundCloud или Яндекс Музыки.
3. **Стратегия В (Рекомендуемая): Гибридная архитектура (yt-dlp как Primary Orchestrator + модульный Go HTTP/HLS Transport для выделенных источников + Web Upload).**
   - *Вердикт:* **Оптимальный путь развития.**
   - *Аргументация:* yt-dlp остается основным рабочим инструментом для YouTube/YouTube Music и общим fallback-экстрактором. При этом для SoundCloud и Яндекс Музыки (где протоколы стабильны и понятны) активируется прямой Go-транспорт.

### 4.2. Жесткое разграничение: резерв транспорта vs смена источника
> [!IMPORTANT]
> **Архитектурный инвариант:** В проекте действует принцип ручной привязки аудиоисточника пользователем.
> - **Резерв транспорта (допустим автоматически):** Если для *одного и того же* выбранного пользователем SoundCloud URL нативный Go HLS загрузчик вернул сетевую ошибку 5xx, система может прозрачно попробовать скачать этот же URL через `yt-dlp`. Сущность аудиозаписи не меняется.
> - **Смена аудиоисточника (запрещена автоматически):** Если трек не скачался с SoundCloud, система **не имеет права** автоматически переключаться на поиск трека в YouTube. Это приводит к рассинхронизации версий (Radio Edit vs Explicit, цензура, живые концерты). Смена источника требует явного действия пользователя в UI.

## 5. Эскиз архитектурной интеграции

Предлагаемый модульный дизайн не ломает существующий код, а формализует границы между резолвером, экстрактором и транспортом на уровне Go-интерфейсов.

### 5.1. Архитектурная схема уровней

```
[Пользователь / Очередь]
       │
       ▼
[Track Identity] (Deezer / Yandex / iTunes Каталог: Title, Artist, Album, ISRC, Duration)
       │
       ▼
[MediaURLResolver] ──► Разрешение в конкретный StreamDescriptor (Stream URL, Type, Auth, Headers)
       │
       ▼
[AudioTransport Router]
       ├──► YtDlpTransport (YouTube, fallback для сложных сайтов)
       ├──► GoHLSTransport (SoundCloud HLS AAC/MP3)
       ├──► GoDirectTransport (Яндекс Музыка signed HTTP / Bandcamp)
       └──► LocalUploadTransport (Пользовательские файлы)
       │
       ▼
[Staging Buffer] (tmp_downloads/{job_id}/raw/01.raw)
       │
       ▼
[Audio Quality & Preview Validation] (ffprobe: проверка >35c и спектральный срез)
       │
       ▼
[ffmpeg Transcoder] (MP3 320 kbps CBR, 44.1 kHz, Joint Stereo)
       │
       ▼
[internal/id3 Engine] (ID3v2.4 UTF-8, null-separated \x00, APIC Cover)
       │
       ▼
[organizer.Service] (Атомарный перенос в MUSIC_DIR по каноническому пути)
```

### 5.2. Контракты интерфейсов (эскиз для будущего внедрения)

```go
package downloader

import (
	"context"
	"io"
	"net/http"
	"time"
)

// StreamType определяет тип протокола доставки потока
type StreamType string

const (
	StreamTypeDirectHTTP StreamType = "direct_http" // Прогрессивный HTTP/HTTPS
	StreamTypeHLS        StreamType = "hls"         // HTTP Live Streaming (.m3u8)
	StreamTypeEncrypted  StreamType = "aes_ctr"     // Зашифрованный поток (Яндекс FLAC)
	StreamTypeYtDlpOnly  StreamType = "ytdlp_raw"   // Источник, требующий yt-dlp extractor
	StreamTypeLocalFile  StreamType = "local_file"  // Локальный файл из веб-аплоада
)

// StreamDescriptor описывает разрешенный для скачивания аудиопоток
type StreamDescriptor struct {
	Type             StreamType        `json:"type"`
	URL              string            `json:"url"`               // Очищенный URL (без секретов в логах)
	DirectURL        string            `json:"-"`                 // Полный подписанный URL
	Headers          http.Header       `json:"-"`                 // Необходимые заголовки (User-Agent, Range)
	ExpectedDuration int               `json:"expected_duration"` // Длительность для валидации превью
	CipherKey        []byte            `json:"-"`                 // Ключ дешифрования для StreamTypeEncrypted
	CipherNonce      []byte            `json:"-"`                 // Nonce/IV
	ExpiresAt        time.Time         `json:"expires_at"`        // Срок жизни подписанной ссылки
}

// AudioTransport абстрагирует физическую доставку байтов в staging
type AudioTransport interface {
	// Name возвращает идентификатор транспорта (e.g., "ytdlp", "go_hls", "go_http")
	Name() string
	// CanHandle проверяет применимость транспорта к данному типу потока
	CanHandle(desc *StreamDescriptor) bool
	// Download скачивает поток в целевой raw-файл внутри sandbox
	Download(ctx context.Context, desc *StreamDescriptor, rawOutPath string, onProgress func(float64)) error
}
```

### 5.3. Механизм обновления протухших URL (Expiring URLs)
Подписанные ссылки Яндекс Музыки и временные HLS-токены SoundCloud живут от 10 минут до 2 часов. Если задача стояла в очереди на паузе или ожидала concurrency-слота:
1. `StreamDescriptor.ExpiresAt` проверяется непосредственно перед передачей в `AudioTransport.Download`.
2. Если `time.Now().After(desc.ExpiresAt.Add(-2 * time.Minute))`, вызывается повторное разрешение `MediaURLResolver.RefreshStream(ctx, desc)`.
3. Пользовательский выбор источника при этом сохраняется (перезапрашивается тот же ID трека в API провайдера).

## 6. Поэтапный план PoC и оценка трудоемкости

### Этап 1: Безопасный HTTP/HLS транспорт на Go (SoundCloud)
- **Цель:** Реализовать скачивание общедоступных HLS-потоков SoundCloud через нативный Go-пайплайн.
- **Области кода:** `internal/services/downloader/transport/` (новый подпакет), `internal/core/safenet/` (SSRF guard).
- **Проверки и Mock-тесты:**
  - Mock HTTP-сервер, отдающий master `.m3u8`, media `.m3u8` и 5 тестовых `.ts` сегментов.
  - Тест отмены `context.Context` посреди скачивания с проверкой удаления незавершенных файлов.
  - Тест SSRF-фильтра: блокировка перенаправлений на `127.0.0.1`, `169.254.169.254`, `10.0.0.1`.
- **Критерий успеха:** Полноценный MP3/AAC файл собирается в staging и успешно проходит штатный `validateDownloadedStreamAudio` и `transcodeToMP3`.
- **Сложность:** Средняя (2–3 рабочих дня).

### Этап 2: Пользовательский веб-импорт (Direct Upload)
- **Цель:** Добавить возможность залить файл напрямую в модальном окне загрузчика.
- **Области кода:** `internal/features/downloader/handlers.go`, `web/templates/components/downloader.html`.
- **Проверки и Mock-тесты:**
  - Mock multipart HTTP POST запрос с файлом 5 МБ.
  - Проверка валидации MIME-типа и ограничений по размеру (`MaxBytesReader`).
  - Проверка корректности работы `PathSandbox` при загрузке файлов с опасными именами (`../../evil.mp3`).
- **Критерий успеха:** Загруженный файл появляется в очереди, распознается теггером и корректно перемещается в `MUSIC_DIR`.
- **Сложность:** Низкая (1–2 рабочих дня).

### Этап 3: Яндекс.Музыка Direct Transport (Опционально)
- **Цель:** Прямое скачивание MP3 320k и дешифрование FLAC через Go без вызова yt-dlp.
- **Области кода:** `internal/services/resolver/client_yandex.go`, новый транспорт в downloader.
- **Проверки и Mock-тесты:**
  - Юнит-тест расчета MD5-хэша подписи по тестовым векторам (salt + path + s).
  - Юнит-тест дешифратора AES-128-CTR на фиксированном зашифрованном буфере.
- **Критерий успеха:** В mock-среде полученный поток декодируется в ожидаемые байты; доступность реального API проверяется отдельно.
- **Сложность:** Средняя (2–3 рабочих дня).
