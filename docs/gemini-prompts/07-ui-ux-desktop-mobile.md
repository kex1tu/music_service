# Промпт 7. UI/UX для ПК и телефонов

Ты работаешь в репозитории music-manager. Улучши UI/UX существующего интерфейса для ПК и телефонов. Нужна реализация с проверкой результата.

Перед началом прочитай AGENTS.md, Architecture.md, plan.md, PROGRESS.md и проектный навык ui-ux-design-system. Изучи текущие шаблоны, стили и Alpine-компоненты. Проверь git status: в рабочем дереве могут быть незакоммиченные изменения — сохрани их и учитывай при работе.

## Целевые экраны

- ПК: примерно 1920×1080, масштаб браузера 100%.
- Телефон: физическое разрешение примерно 2700×1200, в портрете 1200×2700.
- Физические пиксели телефона не равны CSS-пикселям. Ориентируйся на CSS viewport; до уточнения устройства проверяй ширины 360, 390, 412 и 430 CSS px.
- Учитывай панели браузера, экранную клавиатуру, safe-area и изменение доступной высоты.

## Задачи в порядке приоритета

### 1. Мобильная медиатека

Сейчас инспектор тегов расположен перед списком треков. На телефоне основной контент — папки и треки; инспектор открывается по явному действию в отдельной панели.
Для трека показывай название, исполнителя, длительность и меню дополнительных действий. Сохрани доступ к остальным данным и существующим операциям.
После выбора треков показывай контекстную панель массовых действий со счётчиком выбранного.

### 2. Мобильная навигация и мини-плеер

Добавь нижнюю навигацию: «Загрузка», «Медиатека», «Ещё».
Все существующие разделы должны оставаться доступны через «Ещё».
Расположи мини-плеер над навигацией. Согласуй положение очереди, уведомлений и нижних панелей.
Контент, последние строки и кнопки не должны перекрываться фиксированными элементами.
Не дублируй основную навигацию одновременно сверху и снизу.

### 3. Редактор тегов

На ПК используй широкую рабочую область с таблицей и инспектором.
На телефоне сделай полноэкранную компоновку с понятным возвратом, прокруткой содержимого и доступной кнопкой сохранения.
Показывай количество изменённых треков; различай состояния «есть изменения», «сохранение», «сохранено», «ошибка».
Проверь существующую защиту от потери несохранённых изменений и сохрани её.
Используй существующую логику редактирования и сохранения.

### 4. Медиатека на ПК

Сейчас main ограничен max-width 1600px. Дай таблице использовать больше доступной ширины на Full HD, сохрани разумную ширину форм и текста.
Закрепи заголовки таблицы при прокрутке.
Добавь изменение ширины колонок и переключение плотности строк: обычная / компактная. Сохраняй настройки локально без чувствительных данных.
Выделение строк, редактирование, сортировка и горизонтальная прокрутка должны продолжать работать совместно.

### 5. Загрузки и ошибки

Сделай понятными этапы существующего сценария:
поиск → выбор источника → скачивание → проверка тегов → добавление в медиатеку.
Сопоставь подписи с фактическими состояниями приложения. Не выдумывай прогресс и не изображай завершение раньше ответа сервера.
Различай выполняемую операцию, ожидание действия пользователя и ошибку.
При ошибке показывай понятную причину и доступное действие: повторить, выбрать другой источник или проверить ввод — в зависимости от реальных возможностей.
Сохрани отзывчивость интерфейса и существующий polling.

### 6. Читаемость и управление

Обеспечь зоны нажатия минимум 44×44 CSS px на телефоне.
Для основного мобильного текста ориентируйся на 14–16px; ввод не должен вызывать нежелательное увеличение страницы.
Сохрани тёмную палитру и существующие шрифты. Уменьши визуальный вес технических подписей.
Используй единый стандарт Material Symbols SVG.
В каждой рабочей панели выделяй одно главное действие.
Для второстепенных действий используй спокойные кнопки и контекстные меню.
Числа, длительность и прогресс не должны менять ширину при обновлении.

## Ограничения

- Только существующий no-build стек: HTML, Tailwind CDN, Alpine.js, CSS.
- Без Node.js, npm, сборщиков, новых UI-фреймворков и Docker.
- Общее состояние размещай в существующем Alpine.store('app', …); локальное состояние оставляй компонентам.
- Не меняй API, аудиопайплайн, ID3, sandbox и серверную бизнес-логику.
- Не показывай пользователю внутренние названия вроде Puddletag Engine или Command Bar там, где достаточно понятной подписи.
- Не добавляй декоративные градиенты, лишние карточки, анимации и постоянные панели без функциональной необходимости.
- Для диалогов и меню проверь клавиатуру, видимый фокус, Escape, возврат фокуса, aria-атрибуты и блокировку фоновой прокрутки.
- Не выполняй деплой, коммит или push.

## Порядок работы

1. Проверь, какие улучшения уже реализованы. Не дублируй их.
2. Обнови соответствующий раздел plan.md: конкретные изменения и критерии готовности.
3. Реализуй задачи последовательно, начиная с мобильной медиатеки, навигации и редактора.
4. Проверь интерфейс в настоящем браузере на ПК и мобильных CSS-размерах. Добавь проверку короткого viewport с открытой клавиатурой.
5. Проверь длинные названия, пустую медиатеку, большой список, выбор нескольких треков, несохранённые изменения, загрузку и ошибку.
6. Убедись, что нет горизонтального скролла всей страницы. Локальная прокрутка таблицы допустима.
7. Запусти go test -v ./... и штатную сборку:
   go build -ldflags="-s -w" -o bin/music-manager cmd/server/main.go
8. Выполни git diff --check и обнови PROGRESS.md фактическими результатами.

Если инструмент визуальной проверки недоступен, явно укажи это. Не утверждай, что внешний вид проверен по одному чтению кода.

В конце дай компактный отчёт:

- что изменено;
- какие файлы затронуты;
- какие проверки выполнены и их результаты;
- где находятся скриншоты;
- что осталось незавершённым.

Начинай с изучения репозитория, затем переходи к реализации.
