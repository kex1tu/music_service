# Промпт 6. Исследование прямого источника Яндекса

## Правила выполнения

Работай в существующем Music Downloader & Tag Manager. Этот промпт самостоятельный: предыдущая переписка и выполнение остальных промптов не предполагаются.

Перед изменениями прочитай AGENTS.md, Architecture.md, plan.md и последние записи PROGRESS.md. Проверь git status и diff; сохрани чужие незакоммиченные изменения. Открой затрагиваемые файлы и сигнатуры вызываемых методов. Сначала установи, что уже реализовано: указанные ниже точки входа отражают состояние на 9 ноября 2026 года и требуют повторной проверки.

Реализуй только описанную фичу. Обоснуй необходимые изменения смежных областей отдельной записью в plan.md, сохранив остальные планы. Соблюдай Pure Go, отсутствие Node/npm/Python в runtime и Docker, скачивание через yt-dlp, штатную конвертацию ffmpeg в MP3 320 kbps CBR / 44.1 kHz и внутренний ID3v2.4 UTF-8 с null-разделителями. Тексты — только внешние .lrc/.txt. Файловые операции — через PathSandbox.Resolve и существующие safefs/mediaexec; не ослабляй защиту от подмены путей. Итоговые файлы до подтверждения остаются в staging, переносит их organizer.

Не выполняй деплой, коммиты, push и массовые операции с медиатекой. Не используй реальные секреты в коде, фикстурах и логах. Новые настройки отражай в .env.example только при необходимости, без реальных значений. Не делегируй эту же задачу рекурсивно самому себе.

Все внешние HTTP-вызовы в автоматических тестах замокай. Для изменённого кода выполни целевые проверки, затем из корня проекта:

```bash
go test -v ./...
go test -race -p 1 ./...
go vet ./...
CGO_ENABLED=0 go build -ldflags="-s -w" -o bin/music-manager cmd/server/main.go
git diff --check
```

Не ослабляй тесты ради прохождения. Зафиксируй исходные сбои и ограничения среды. Обнови PROGRESS.md: что реализовано, что проверено и что заблокировано. В финале перечисли изменения с файлами, результаты команд, ограничения и непроверенное поведение. Успешные mock-тесты не доказывают доступность внешнего API в production.

## Задача и результат

Подготовь техническое решение по получению аудио Яндекса напрямую. На этом этапе результат — исследовательская записка и план интеграции. Код скачивания, криптографию, production-конфигурацию и whitelist не меняй.

Общие команды тестирования из правил ниже обязательны для изменения исполняемого кода; для одной записки достаточно проверки документа и diff. Код в рамках этого задания не требуется.

## Причина отдельного исследования

AGENTS.md, раздел 2, пункт 4 закрепляет скачивание за yt-dlp. Собственная HTTP-загрузка с AES-дешифрованием на Go конфликтует с этим правилом. Нельзя самостоятельно заменить инвариант или считать этот промпт разрешением на его обход.

## Что исследовать

1. Изучи https://github.com/llistochek/yandex-music-downloader : зафиксируй commit, лицензию и ссылки на конкретный код протокола. Отдели подтверждённое исходниками от предположений о доступности API.
2. Проверь возможности именно используемого standalone yt-dlp: поддержку Яндекса, авторизации, форматов, proxy и необходимого потока. Укажи версию и первичные источники. Не считай поддержку метаданных доказательством скачивания.
3. Сравни два пути: штатный yt-dlp при подтверждённой поддержке и отдельный Go transport, требующий изменения архитектурных правил.
4. Опиши необходимые условия доступа без извлечения пользовательских токенов и реальных платных загрузок. Не обещай доступ без подписки или гарантированную скорость.
5. Для Go-варианта опиши раздельно подпись запроса и расшифровку: происхождение ключей, IV/счётчик AES-CTR, точные параметры и срок действия URL. Не выводи секреты и не копируй встроенные ключи в записку.
6. Предложи интерфейс, отделяющий каталожную ссылку от временного URL. Покажи, как сохранить ручной выбор источника, пережить рестарт, обновить истёкшую ссылку и исключить чувствительные URL/ключи из логов и DB.
7. Опиши staging, отмену/таймауты, proxy, лимиты, проверку скачанного файла и обязательное завершение штатным ffmpeg → MP3 320 kbps CBR / 44.1 kHz → внутренний ID3v2.4. Частичные файлы не могут стать ready.
8. Перечисли необходимые изменения областей проекта и mock/crypto/integration проверки. Автоматический переход на другой аудиоисточник при ошибке не предлагай как поведение по умолчанию.

## Критерии готовности

Записка содержит подтверждённые возможности yt-dlp, ограничения доступа, сравнение вариантов, рекомендуемый путь, конкретные файлы/интерфейсы, план проверок и открытые вопросы. Если необходим Go transport, явно зафиксируй конфликт в PROGRESS.md и минимальное архитектурное решение, которое требуется от владельца проекта. Независимые фичи из других промптов этим исследованием не блокируются.

Не представляй исследование как реализованное прямое скачивание. Реализация выбранного пути — отдельное следующее задание после разрешения конфликта.
