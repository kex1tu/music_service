# Промпт 4. Проверка защиты от коротких аудиопревью

## Правила выполнения

Работай в существующем Music Downloader & Tag Manager. Этот промпт самостоятельный: предыдущая переписка и выполнение остальных промптов не предполагаются.

Перед изменениями прочитай AGENTS.md, Architecture.md, plan.md и последние записи PROGRESS.md. Проверь git status и diff; сохрани чужие незакоммиченные изменения. Открой затрагиваемые файлы и сигнатуры вызываемых методов. Сначала установи, что уже реализовано: указанные ниже точки входа отражают состояние на 9 ноября 2026 года и требуют повторной проверки.

Реализуй только описанную фичу. Обоснуй необходимые изменения смежных областей отдельной записью в plan.md, сохранив остальные планы. Соблюдай Pure Go, отсутствие Node/npm/Python в runtime и Docker, скачивание через yt-dlp, штатную конвертацию ffmpeg в MP3 320 kbps CBR / 44.1 kHz и внутренний ID3v2.4 UTF-8 с null-разделителями. Тексты — только внешние .lrc/.txt. Файловые операции — через PathSandbox.Resolve и существующие safefs/mediaexec; не ослабляй защиту от подмены путей. Итоговые файлы до подтверждения остаются в staging, переносит их organizer.

Не выполняй деплой, коммиты, push и массовые операции с медиатекой. Не используй реальные секреты в коде, фикстурах и логах. Новые настройки отражай в .env.example только при необходимости, без реальных значений. Не делегируй эту же задачу рекурсивно самому себе.

Все внешние HTTP-вызовы в автоматических тестах замокай. Для изменённого кода выполни целевые проверки, затем из корня проекта:

```bash
go test -v ./...
go test -race -p 1 ./...
go vet ./...
CGO_ENABLED=0 go build -ldflags="-s -w" -o bin/music-manager cmd/server/main.go
git diff --check
```

Не ослабляй тесты ради прохождения. Зафиксируй исходные сбои и ограничения среды. Обнови PROGRESS.md: что реализовано, что проверено и что заблокировано. В финале перечисли изменения с файлами, результаты команд, ограничения и непроверенное поведение. Успешные mock-тесты не доказывают доступность внешнего API в production.

## Задача

Проверь полноту существующей защиты от коротких превью и исправь только подтверждённые пробелы. Повторная реализация механизма не нужна.

## Исходное состояние

В internal/services/downloader/media_processor.go уже существуют downloadAndValidateRawStream и validateDownloadedStreamAudio. Проверка использует длительность ffprobe: actual <35 секунд при expected >60 секунд. В media_processor_test.go есть синтетический тест. Проверь актуальное состояние этих функций.

## Работа

1. Проследи все пути загрузки, повторной попытки и смены версии. Установи, что проверка вызывается до конвертации/готовности файла.
2. Проверь, откуда берётся expectedDuration. Для проверки полноты трека нужна длительность ожидаемой композиции; длительность найденного 30-секундного кандидата не должна маскировать превью.
3. Сохрани легитимные короткие треки и текущие пороги. Эвристика короткого превью не доказывает региональную блокировку или цензуру.
4. Явно определи поведение для неизвестной длительности, пустого/нечислового значения, NaN/Inf, malformed JSON, ошибки ffprobe, таймаута и отмены. Не вводи скрытых изменений политики: обоснуй необходимые отличия в плане.
5. Проверь состояние очереди после отказа: частичный/невалидный файл не становится ready, ссылка ручного выбора не теряется, другой источник автоматически не назначается.
6. При необходимости поправь понятное сообщение об ошибке в действующем UI, сохранив безопасный вывод текста.
7. Если механизм уже корректен и покрыт тестами, дай доказательства и не создавай искусственные правки.

## Приёмка

Проверь actual ниже/на/выше 35 секунд, expected ниже/на/выше 60, короткий легитимный трек, неизвестную ожидаемую длительность и ошибки probe. Покрой реально найденный пробел регрессионным тестом. Используй фикстуры или синтетический звук; реальные треки и внешняя сеть не нужны.

Не меняй форматы конвертации, matcher, набор источников и логику цензурного аудита.
