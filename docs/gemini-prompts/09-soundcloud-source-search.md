# Промпт 9. Поиск SoundCloud в окне выбора источника

Реализуй в Music Downloader & Tag Manager прямой поиск SoundCloud внутри выбора аудиоисточника трека и цельного релиза. Пользователь должен открыть небольшое окно, изменить запрос, просматривать треки/альбомы/плейлисты с загрузкой следующих страниц и выбрать результат для текущей задачи. Исправь ограничения существующего подбора релизов, из-за которых доступных результатов оказывается мало.

## Правила работы

Это самостоятельное задание, предыдущая переписка не требуется. Сначала прочитай AGENTS.md, Architecture.md, plan.md и последние записи PROGRESS.md. Проверь git status/diff, сохрани чужие и незакоммиченные изменения. Перед изменением открой файл; перед использованием метода проверь его реальную сигнатуру. Прочитай применимые навыки UI/UX, systematic-debugging и Go-тестирования. Не делегируй задачу рекурсивно.

Сначала проследи текущий поток данных и воспроизведи причины потери результатов на mock-ответах. Изменения смежных областей resolver/downloader/API/frontend обоснуй в plan.md, не заменяя остальные планы. Не делай общий редизайн.

Соблюдай Pure Go, отсутствие Python/Node/npm в runtime, отсутствие Docker. Фронтенд — существующие Alpine.js/Tailwind CDN, общее состояние в Alpine.store. Скачивание остаётся через yt-dlp, конвертация через ffmpeg в MP3 320 kbps CBR / 44.1 kHz, теги через internal/id3, ID3v2.4 UTF-8 с null-разделителями; тексты только внешние .lrc/.txt. Файловые операции — через PathSandbox.Resolve и существующие safefs/mediaexec. Файлы до подтверждения остаются в staging, переносит organizer.

Не выполняй деплой, коммиты, push, массовые операции с медиатекой. Не читай и не раскрывай .env, cookies, токены и другие секреты. Не требуй учётные данные пользователя для реализации. Не добавляй новые настройки без необходимости; если они потребуются, документируй плейсхолдерами в .env.example.

## Текущее поведение и причины ограничения выдачи

На момент постановки задания подбор релиза запрашивает первые страницы search/albums и search/playlists_without_albums, чередует результаты, удаляет повторы и обрезает их до общего лимита 30. «Больше» перезапрашивает начало с лимитом 60/90/100. После получения треклистов кандидаты без доступных треков отбрасываются. UI вычисляет hasMoreSoundCloud по числу оставшихся кандидатов относительно лимита, поэтому после отсева кнопка может исчезнуть при наличии следующих страниц. Наше ранжирование меняет порядок SoundCloud.

Отдельный поиск SoundCloud уже запрашивает треки/альбомы/плейлисты по 10, но вычисляет следующий offset самостоятельно; NextHref используется лишь как признак. Этот код нужно переиспользовать и улучшить, а не писать второй несвязанный поисковик.

## Требуемый интерфейс

1. В обоих выборах источника добавь действие «Искать в SoundCloud». Открывается компактное окно поиска с сохранением родительского контекста. На телефоне допустим адаптивный полноэкранный диалог. Не используй iframe сайта SoundCloud.
2. Запрос предзаполняется исполнителем и названием трека/альбома и свободно редактируется. Поиск запускается Enter или кнопкой. Вкладки: «Треки», «Альбомы», «Плейлисты». Для трека по умолчанию открыты треки; для цельного релиза — альбомы/плейлисты. Одиночный трек нельзя привязать как целый релиз; коллекцию нельзя молча привязать как одиночный трек.
3. Покажи название, автора/загрузившего пользователя, длительность либо количество треков, ссылку на SoundCloud; обложку — если она доступна без тяжёлых дополнительных запросов. Различай автора загрузки и подтверждённого исполнителя. Отсутствующие метаданные не должны убирать результат.
4. Сохраняй порядок API внутри типа. Не применяй наше ранжирование соответствия, цензуры и версий к просмотру выдачи; такие проверки выполняются при выборе и сопоставлении. Не обещай идентичность выдаче сайта при другой сессии, регионе или параметрах. Цель — все страницы, доступные через используемый endpoint для запроса, без искусственного потолка 100 и скрытого отсева по треклисту.
5. «Загрузить ещё» догружает следующую страницу активной вкладки, сохраняя список и прокрутку. Состояния загрузки, пустого результата, конца выдачи и ошибки различаются. Ошибка одной категории не блокирует остальные. Повтор ошибки загружает ту же страницу.
6. Выбор результата загружает его детали и возвращает его в текущий picker. В режиме релиза покажи треклист/соответствие и используй существующий ручной remap. Поиск и выбор не должны сами запускать новую задачу, preflight новой загрузки или скачивание. Привязка/скачивание происходит штатным явным подтверждением родительского picker.
7. Закрытие поиска отменяет/обесценивает его незавершённые запросы, возвращает фокус в родительский picker и не теряет выбранный источник, target tracks, job/track/path и ручные сопоставления. При переключении контекста устаревший ответ не должен попасть в другую задачу.
8. Сохрани отдельный поиск SoundCloud в основном загрузчике с его текущим действием «Предпросмотр и скачивание». Общую логику вынеси в переиспользуемый store/модуль с явным режимом результата, без случайного смешения состояний поиска и контекстов.

## Backend и пагинация

- Используй существующий прямой поиск SoundCloud. Документируй, что api-v2 — веб-API, и не подменяй его возможностями официального API без проверки. Если уточняешь внешний контракт, проверь актуальные первичные источники; сетевые запросы в автоматических тестах запрещены.
- Введи явный контракт продолжения для каждой категории и фиксированного запроса. Ориентируйся на реальное next_href/курсор ответа, не на количество элементов после фильтрации или равенство page size. Не вычисляй продолжение арифметически, если upstream возвращает иные параметры. Не смешивай страницы разных запросов/вкладок.
- Сохраняй совместимость существующих потребителей endpoint либо обнови все вызовы и тесты одним изменением. Клиент не должен передавать серверу произвольный URL для сетевого запроса. Выбери безопасный ограниченный token/проверяемые параметры продолжения, связанные с запросом и категорией; объясни решение.
- Не следуй next_href без проверки: схема, точный разрешённый host/port, endpoint, параметры и редиректы. Запрети переходы на чужие/внутренние адреса и передачу секретов другому host. Не логируй чувствительные URL/client_id/токены. Ограничь размер ответа, длины параметров, page size, таймауты и число параллельных запросов.
- Сохрани штатное обновление client_id при 401/403, исключи бесконечные retry. 429 и временные ошибки должны давать понятное состояние с возможностью повторить, без потери уже загруженного списка.
- Убирай повторы по стабильному ID/каноническому URL с сохранением порядка. Отбрасывать разрешено некорректные/небезопасные записи, но это не должно скрывать продолжение. Не загружай треклисты всех результатов для построения поисковой страницы.
- Защити от циклического/повторяющегося курсора и повторных запросов одной страницы. Не создавай бесконечную подгрузку пустых страниц. Защитные пределы должны быть явными и обоснованными; не возвращай скрытый потолок 100.

## Исправление существующего подбора

Исправь раннее исчезновение «Больше альбомов и плейлистов SoundCloud». Наличие продолжения должно определяться upstream-пагинацией до фильтрации. Замени перезапрос первых N результатов на последовательные страницы с независимым продолжением альбомов и плейлистов, сохранив текущие YT Music-кандидаты и выбранный результат. Не сбрасывай ручной remap при добавлении страниц.

В автоматическом подборе допустимо сохранить наше ранжирование. В окне прямого поиска порядок остаётся как у SoundCloud. Расширение лимита поиска отдельных треков через scsearch само по себе не заменяет эту задачу; не меняй несвязанные провайдеры.

## Проверки и критерии готовности

Добавь содержательные mock-тесты:

- Несколько страниц каждого типа, next_href с неарифметическим продолжением; конец выдачи не определяется размером страницы.
- После фильтрации/дедупликации осталось меньше page size или ноль, но продолжение не потеряно. Кнопка не исчезает из-за недоступных треклистов.
- Более 100 результатов доступны последовательными страницами без перезапроса начала и без повторной выдачи старых элементов.
- Частичный отказ категорий, 401/403 с одним обновлением client_id, 429, timeout, отмена, retry той же страницы.
- Недопустимый/чужой next_href, подмена категории/запроса, вредоносные URL, чрезмерный ответ, циклическое продолжение.
- Поисковая страница не вызывает загрузку треклистов; выбранный результат проходит штатную загрузку деталей. Сбой деталей не удаляет результат и не меняет текущую привязку.
- Выбранные URL, job/track/path и remap сохраняются при догрузке; устаревшие ответы игнорируются; поиск не запускает скачивание.

Проверь UI реальным браузером/Playwright доступными средствами без npm: desktop около 1920×1080 и mobile 360/390/412/430 CSS px. Проверь прокрутку, отсутствие горизонтального переполнения, клавиатуру, Escape, focus trap/восстановление фокуса, доступные подписи и корректную работу вложенных диалогов. Физические 1200×2700 телефона не являются CSS viewport. Для воспроизводимой проверки используй тестовые данные/моки. Если браузерная проверка недоступна, явно зафиксируй это.

go test -race -p 1 ./...
go vet ./...
go build -ldflags="-s -w" -o bin/music-manager cmd/server/main.go

Не ослабляй проверки ради зелёного результата. Исходные сбои и ограничения среды отметь отдельно. Обнови PROGRESS.md фактическими изменениями и проверками. Если меняются статические ресурсы, используй существующий механизм обновления их версий.
