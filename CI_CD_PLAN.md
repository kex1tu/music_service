# План CI/CD Music Manager

Дата: 2026-11-10. Редакция: итоговая после v4.1.
Статус: **PLANNED — реализация и развёртывание по этому документу не выполнялись**.

Это единая спецификация вместо разрозненных редакций v1–v4.1. При расхождении с примерами из переписки действуют требования этого файла. Примеры интерфейсов ниже, явно обозначенные как новые, ещё не существуют в коде.

## 1. Результат и границы

Обычный выпуск проходит путь:

`PR → проверки → merge/push main → проверки → один статический артефакт → server2 → health + две живые Deezer-проверки → квитанция → завершение автоматического запуска`.

Продвижение на `nl_music` запускает оператор отдельным `workflow_dispatch`: выбирается проверенный canary-прогон, скачивается его исходный артефакт, проверяются квитанция и SHA256, выполняется установка без пересборки. На `push` основной сервер никогда не обновляется. GitHub Required reviewers можно использовать дополнительно, но от доступности этой функции схема не зависит.

При сбое `server2` откатывается только `server2`, production не затрагивается. При сбое `nl_music` откатывается только `nl_music`, проверенная версия на `server2` остаётся для диагностики.

Разрешён отдельный ручной режим `emergency_nl_music_hotfix`: обязательные lint/test/build сохраняются; пропуск canary явно фиксируется в отчёте. Такой выпуск не создаёт canary-квитанцию.

Документ не разрешает реализацию, деплой или изменение состояния серверов сам по себе. В текущей задаче подготавливаются только документация и ссылки на неё.

### 1.1. Инварианты

- Pure Go, единый статический бинарник `bin/music-manager`, без Python/Node.js runtime, npm и Docker.
- Скачивание через yt-dlp, ffmpeg: MP3 320 kbps CBR / 44100 Hz; теги через `internal/id3`: ID3v2.4 UTF-8, множественные значения `\x00`. Тексты только рядом с MP3.
- Все пользовательские файловые пути проходят `PathSandbox.Resolve()`, файловые операции — через descriptor-relative `safefs`/`mediaexec`. Существующий `safefs.RemoveAll` принимает один разрешённый путь.
- Промежуточное аудио остаётся в `TMP_DIR/{job_id}`; эксплуатационная проверка не подтверждает перенос в `MUSIC_DIR`.
- Любые установки, резервирование, health, откат и серверные операции продвижения выполняются через `scripts/deploy.sh`. Прямых SSH/scp-команд в workflow нет.
- Секреты не попадают в Git, stdout, `set -x`, артефакты или журналы диагностики.
- Все внешние HTTP-вызовы в `go test` замоканы. Живые обращения разрешаются отдельной оговоркой в AGENTS.md только для эксплуатационной приёмки canary, вызываемой из deploy.sh. До внесения оговорки этот этап не включается.

### 1.2. Области изменений

## 2. Workflow и происхождение артефакта

### 2.1. Матрица запусков

| Событие / режим | lint/test | build | server2 + probe | nl_music |
|---|---|---|---|---|
| `pull_request` в main | да | нет | нет | нет |
| `push` main | да | один раз | да | нет |
| dispatch `deploy_canary_server2` на main | да | один раз | да | нет |
| dispatch `promote_canary_to_nl_music` на main | пропустить | пропустить | проверить существующую квитанцию | исходный артефакт |
| dispatch `emergency_nl_music_hotfix` на main | да | один раз | нет | новая сборка с явной отметкой обхода |

Джоба promotion не имеет `needs` на пропущенные lint/test/build/canary. Остальные зависимости задаются явно: `lint → test → build → deploy-canary-server2`; emergency зависит от build. На `push` нет условия, разрешающего production.

`workflow_dispatch.inputs`: `mode` с тремя значениями из таблицы и необязательный `canary_run_id` (строка из цифр). Непустой ID должен совпадать с текущей проверенной квитанцией. Выбор исторического прогона, отличного от работающего на canary, не поддерживается: сначала нужно вернуть соответствующий проверенный выпуск на canary.

Деплой разрешён только для `refs/heads/main`. PR-проверки не получают серверные секреты. Задать минимальные `permissions`: `contents: read`, а для promotion также `actions: read`. Production concurrency — одна общая группа для всех запусков, меняющих эти серверы; `cancel-in-progress: false`. PR используют отдельную группу с отменой устаревших проверок. Серверный lock дополнительно защищает от локального запуска вне Actions.

### 2.2. Сборка и хранение

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath \
  -ldflags="-s -w" -o bin/music-manager cmd/server/main.go
```

Проверить ELF, отсутствие динамического интерпретатора/зависимостей и SHA256. Хранить артефакт `music-manager-${GITHUB_SHA}` минимум 14 дней. Манифест включает полный commit, SHA256 бинарника, run ID, run attempt, версию Go и параметры сборки. Проверка воспроизводимости означает отдельную повторную сборку и сравнение; один `-trimpath` сам по себе её не доказывает.

`SKIP_LOCAL_BUILD=1` означает установку ровно загруженного файла: запрещены скрытая пересборка и подмена артефакта. Обязателен `EXPECTED_BINARY_SHA256`; его проверяют до отправки, на staging-файле сервера и у `/proc/$MAINPID/exe`. `SKIP_LOCAL_TESTS=1` разрешён в CI только после успешной проверки этого артефакта/его исходного canary-прогона. При обычном локальном вызове deploy.sh выполняет проверки и сборку сам.

### 2.3. Canary-квитанция и promotion

После прохождения health, двух ссылок, очистки probe-задач и восстановления исходного состояния очереди атомарно записать `${APP_DIR}/deploy-backups/canary-verified.json`. Поля:

`schema_version`, `deployment_id`, `git_commit`, `binary_sha256`, `ci_run_id`, `ci_run_attempt`, `smoke_urls_verified`, `verified_at_utc`, `status: verified`.

Квитанция — доверенный серверный документ с ограниченными правами, доставляемый по проверенному SSH; без реально реализованной подписи не называть её криптографически подписанной. Она привязана к точному бинарнику, а не только к названию ветки. После emergency/неуспешной установки нельзя выдавать новую verified-квитанцию.

Promotion выполняет:

1. `deploy.sh server2 --verify-and-print-canary-receipt [expected_run_id]`: проверить схему/поля, обе ссылки, успешный исходный run и соответствие SHA256 работающему процессу canary. Проверить принадлежность GitHub run этому репозиторию и разрешённому workflow/ref; не доверять одному имени артефакта.
2. `gh run download <run_id> -n music-manager-<full_commit> -D <fresh_staging_dir>`. У GitHub токена должны быть права чтения Actions. Не извлекать поверх остатков предыдущей попытки.
3. При недоступности артефакта — `deploy.sh server2 --fetch-verified-binary <destination> --expected-sha256 <sha> --expected-run-id <id>`. Под server2-lock скопировать снимок того же исполняемого файла/проверенного релиза, затем проверить его SHA256. Нельзя просто читать меняющийся `bin/music-manager` без сверки.
4. Сверить загруженный файл с исходной квитанцией, повторно проверить canary-предпосылки перед production. При гонке или смене canary — остановиться, не выбирать новый выпуск автоматически.
5. `deploy.sh nl_music --expected-sha256 <sha>` устанавливает этот файл без сборки. Манифест production сохраняет происхождение canary и фактический commit скриптов установки.

Сервисные подкоманды deploy.sh не запускают обычные фазы сборки/установки и не ставят очередь на паузу. Только JSON/бинарный результат идёт в stdout, вся диагностика — в stderr. Используется единый SSH-транспорт с портом из target-конфигурации (в текущем deploy.sh — 56924), `BatchMode=yes`, `StrictHostKeyChecking=yes`, закреплённым known_hosts и ограниченными таймаутами.

## 3. Транзакция deploy.sh

### 3.1. Доверенная конфигурация и lock

Цели: `server2`, `nl_music`, `all`. Для `all` последовательно запускаются отдельные дочерние процессы `server2 → nl_music`, только при успехе первого. Это локальный маршрут того же конвейера с обязательным canary/probe; автоматический GitHub push его не вызывает.

Фактические `WorkingDirectory`, пользователь/группа, HOST/PORT, DATABASE_PATH, TMP_DIR, MUSIC_DIR и источники окружения читаются для каждого сервиса отдельно. Приоритет значений должен соответствовать реальному окружению процесса и загрузке Config. Не исполнять `.env` через `source`/`eval`. Не выводить `Environment` целиком. Относительные пути разрешать от WorkingDirectory, IPv6 и bind-host обрабатывать явно. Порты 3000/8010 из прежних отчётов — сведения для сверки, не источник конфигурации.

Один владелец удерживает эксклюзивный серверный flock на весь период preflight/backup/install/probe/cleanup/rollback. Standalone probe использует тот же lock; дочерний probe внутри деплоя наследует владение, а не захватывает его повторно. Lock должен удерживаться на удалённом сервере, а не только в GitHub runner. Двухсерверные операции берут locks в одном порядке: server2, затем nl_music.

Перед новым деплоем проверить незавершённый удалённый журнал предыдущей транзакции. После SIGKILL, обрыва SSH или перезагрузки EXIT trap не гарантирован: новая установка запрещена до проверки/завершения recovery. Recovery возвращает только бинарник и сверяет состояние; повторный запуск должен быть идемпотентным.

### 3.2. Фазы и точка фиксации

1. **Preflight:** конфигурация, разрешения, SSH/known_hosts, активность старой версии, runtime yt-dlp/ffmpeg/ffprobe и необходимых вспомогательных инструментов; совместимость схемы, доступность API эксплуатации, свободное место.
2. **Подготовка:** сохранить исходную пользовательскую паузу; установить отдельный deployment hold, дождаться завершения активных исполнителей с ограниченным таймаутом. Создать проверенный бандл бинарника и SQLite. Ошибка этого этапа не заменяет бинарник, но снимает собственный hold.
3. **Установка:** выставить `TX_ACTIVE=1`, передать новый файл в staging на той же ФС, проверить SHA256/права/владельца и атомарно переименовать.
4. **Restart:** запустить сервис; ограничения очереди читаются до запуска worker pool, см. §5.
5. **Приёмка:** health для обоих серверов, для server2 обязательно две живые ссылки. Очистить только свои probe-задачи. Восстановить состояние очереди и подтвердить его.
6. **Commit:** атомарно записать `manifest.status=succeeded`, обновить `last-good`, на server2 опубликовать verified-квитанцию; только затем `TX_ACTIVE=0`. Ротация и прочее обслуживание выполняются после commit. Ошибка обслуживания даёт отдельный ненулевой результат без отката уже принятого релиза.

Частично записанная квитанция/manifest недопустима: временный файл, fsync и атомарная замена. Журнал состояния позволяет различить принятый релиз и незавершённую установку после аварии между шагами commit.

### 3.3. Health gate

- systemd active и корректный MainPID; путь executable принадлежит ожидаемой установке, SHA256 `/proc/$PID/exe` совпадает с артефактом.
- Локальный и публичный HTTPS `/api/health` отвечают ожидаемым JSON и 200; проверить актуальный встроенный UI-ассет. Для публичной проверки исключить ложный успех из кэша.
- `PRAGMA quick_check` живой SQLite возвращает `ok`; ошибка открытия отсутствующего файла не должна молча создавать пустую БД.
- Повторять проверки ограниченное время, например до 120 секунд, с per-request timeout. Системные логи снимать только в диапазоне текущей установки, с удалением чувствительных данных.

### 3.4. EXIT, сигналы и rollback

`set -Eeuo pipefail`; обычные фазовые функции не вызывать через `if ! phase`, `phase || ...` и другие контексты, подавляющие errexit. Обработчики INT/TERM выставляют 130/143 и вызывают exit; EXIT сохраняет исходный код команды или сигнала.

Состояние: `TX_ACTIVE`, `TX_ROLLBACK_DONE`, `TX_SIGNAL_EXIT_CODE`, `TX_QUEUE_STATE_MANAGED`, исходная пользовательская пауза, target, deployment ID, bundle, пути и порт. Это отдельный контекст каждого target-процесса.

В EXIT отключить errexit для диагностики, обеспечить однократный rollback и защиту от повторного INT/TERM внутри ограниченной процедуры восстановления. Все значимые результаты проверяются явно: отсутствие errexit не означает игнорирование ошибок.

При незавершённой установке:

1. Остановить сервис и подтвердить завершение его писателей/дочерних процессов.
2. При целой живой БД выполнить проверяемый checkpoint и quick_check; бинарник N-1 восстановить через staging и атомарный rename, а не перезапись исполняемого inode.
3. Запустить N-1, проверить hash/health, убрать собственный hold и сверить исходную пользовательскую паузу. Ошибка rollback отмечается `rollback_failed`, а не `rolled_back`.
4. При повреждённой БД оставить сервис остановленным, вернуть бинарник при возможности, сохранить диагностику. Не запускать его ради восстановления очереди: записать `queue_restore_pending` для ручного recovery.

Пауза/hold восстанавливаются и при `TX_ACTIVE=0`, если скрипт уже изменил состояние очереди. Ошибка восстановления не подавляется; код выхода ненулевой, флаг незавершённого восстановления остаётся в журнале. Прежние сигнальные коды не заменяются нулём.

## 4. SQLite, резервирование и ротация

Бандл `${APP_DIR}/deploy-backups/${DEPLOYMENT_ID}` содержит `music-manager.prev`, `library.db.prev`, `manifest.json`. В manifest: предыдущий/новый SHA256, версия схемы, исходное состояние очереди, фаза, статус и времена. Права прежнего бинарника сохраняются; права БД берутся из проверенного владельца сервиса, без предположения, что оба сервера одинаковы.

Снимок работающей БД создаётся Online Backup API (sqlite3 `.backup` с корректным экранированием пути), с busy timeout и общим wall-clock timeout. Проверить полный результат `PRAGMA integrity_check == ok` до swap. Копирование только `library.db` через cp при активном WAL запрещено.

Свободное место проверяется по фактическим файловым системам bin, deploy-backups, DB и TMP_DIR. Учесть db + wal + shm, прежний и новый бинарники, снимок, checkpoint и staging/probe с запасом. Размеры считать безопасно при ротации WAL; отсутствующие целевые каталоги обрабатывать через существующий родительский mount. Нет фиксированного обещания «не больше 150 МБ».

Миграции N должны быть проверены с N-1: одних аддитивных DDL недостаточно, требуется совместимость SQL-запросов, значений, сохранённых заданий и startup-процедур. Автоматический rollback **никогда не восстанавливает старый снимок БД**. Не обещать сохранение 100% данных без испытания совместимости и учёта аварийно прерванных работ.

Ручное восстановление: `deploy.sh <target> --manual-db-restore <deployment_id> --i-accept-data-loss-since-backup`. Под lock остановить писателей, переместить текущие db/wal/shm в карантин, восстановить проверенный снимок и права, запустить подходящий бинарник и синхронизировать файловый индекс через подтверждённый API. Оператор видит время снимка и окно возможной потери. Карантин не удалять автоматически.

Ротация: пять последних успешных бандлов плюс не более двух неуспешных **незащищённых**. Текущий, last-good, незавершённый recovery и карантин защищены отдельно и могут увеличивать общий объём. Проверять manifest до учёта квот. Без NUL-unsafe `ls | xargs` и word splitting. Удалять только валидированные прямые дочерние bundle-каталоги доверенного backup root; не следовать симлинкам. Низкоуровневое удаление реализовать через sandbox-aware Go-операцию, вызываемую deploy.sh, без общего `rm -rf` по входному пути.

Служебный CLI-режим того же бинарника делегирует операции новому `internal/ops/`, не запускает HTTP, scanner, миграции и startup-сброс библиотечных таблиц. Корень операций берётся из доверенной target-конфигурации; каждый путь проверяется PathSandbox. Правила хранения и удаления остаются внутри контура deploy.sh, отдельного runtime-бинарника не добавляется.

## 5. Пауза пользователя, deployment hold и probe

Восстановление `.is_paused` через HTTP после restart недостаточно: worker мог уже запуститься. Поэтому пользовательская пауза хранится персистентно и загружается **до** старта worker pool. Отдельный персистентный deployment hold запрещает новые пользовательские исполнения, не подменяя пользовательский pause/resume.

Новые административные контракты (под существующей авторизацией, требуют реализации и описания в API.md):

- capabilities: версия deployment-протокола, синхронный delete, поддержка persisted pause/hold/probe;
- acquire/release deployment hold: владелец — уникальный deployment ID, изменения чужого hold запрещены;
- создание operational probe: существующий POST /downloads расширяется необязательным полем `probe_deployment_id`, принимаемым только при соответствующем активном hold; задача неизменяемо помечается как probe;
- summary сообщает пользовательскую паузу, hold, число queued и активных исполнителей отдельно.

Probe-задачи обходят только deployment hold и пользовательскую паузу для своего конкретного ID. Они не снимают глобальную паузу и не запускают пользовательскую очередь. Hold применяется к Start/Retry/Bind/SwitchRelease и другим путям запуска; пробуждение pool не должно обходить проверку. Пользовательский pause/resume сохраняет свой смысл и не снимает deployment hold. Изменение паузы пользователем во время операции не перезаписывается устаревшим снимком: сверять ревизию состояния или не менять пользовательскую паузу вообще.

Первое включение требует подготовительной совместимой версии: N-1 должен понимать эти ограничения и не сбрасывать/портить пользовательские задания при старте. До этого автоматический транзакционный деплой с обещанием сохранения очереди запрещён. Bootstrap выполняется отдельно через deploy.sh в согласованном обслуживании, с отсутствием активных/ожидающих пользовательских работ и проверенными предпосылками; он не объявляется обычным безостановочным rollout. Если предпосылки не соблюдены, preflight завершается до мутаций.

Хранить токен сессии и SECRET_KEY только на целевом сервере. Не формировать SSH-команду с токеном на стороне runner: удалённый helper сам читает необходимые значения и делает локальные HTTP-вызовы. Учитывать реальный SESSION_COOKIE_NAME, SessionTTL и нормализацию login. Собственного короткого TTL в существующем формате HMAC-токена нет.

## 6. Жизненный цикл задач и синхронный DeleteJob

### 6.1. Исполнители

На задачу нужен стабильный объект lifecycle с `deleting`, реестром активных исполнителей и каналом завершения текущего поколения. Регистрировать исполнителя атомарно с проверкой существования/deleting/ограничений **в точке фактического исполнения**, а не повторно при постановке в очередь и при её чтении.

Каждый активный исполнитель имеет свой ID и CancelFunc. Не использовать накапливающуюся цепочку `prevCancel`: завершённые регистрации удаляются, память ограничена реально активными исполнителями. При переходе 0 → 1 создать новый done-канал; при 1 → 0 закрыть его ровно один раз. Defer release обязателен на всех путях, включая ошибку до запуска subprocess. Release сверяет захваченный объект/generation, а не произвольное новое состояние по тому же ID.

Start/Retry/Bind/SwitchRelease/Backfill и все пути записи файлов участвуют в одном протоколе. Метаданные, таймеры и ожидающие элементы queue не должны запускать работу после tombstone. Контекст исполнения принадлежит сервису/задаче, а не завершившемуся HTTP-запросу. Отмена ожидает реальный выход дочерних yt-dlp/ffmpeg; закрытие Go-канала до завершения процессов не считается остановкой.

### 6.2. Порядок удаления

1. Сериализовать DELETE одной задачи; под jobsMu атомарно проверить существование и установить deleting. Заблокировать все новые запуски/мутации этой задачи, захватить snapshot CancelFuncs и done-канал.
2. Освободить jobsMu, отменить всех исполнителей и дождаться завершения с ограничением 15 секунд и контекстом запроса. Не удерживать jobsMu при cancel, ожидании, SQL или файловых операциях.
3. При таймауте оставить tombstone: повторный DELETE продолжает очистку, retry/bind пока запрещены. Не «разблокировать» задачу с ещё работающим процессом.
4. Под timersMu остановить/удалить timer. `Timer.Stop()==false` не гарантирует завершения callback — его запись синхронизируется следующим пунктом.
5. Все SaveJob одной задачи (таймер, терминальное состояние, другие прямые сохранения) и финальный SQL DELETE проходят через общий per-job persistence mutex. Save под этим mutex повторно проверяет существование/deleting/generation, затем пишет snapshot. Callback после удаления обязан пропустить запись.
6. После остановки писателей разрешить каталог через tmpSandbox.Resolve(jobID, false), затем safefs.RemoveAll(jobDir). Отсутствующий каталог допустим; иные ошибки вернуть.
7. Под persistence mutex удалить запись из SQLite; при успехе под jobsMu удалить s.jobs и lifecycle. Таймаут/ошибка БД после удаления папки остаются повторяемой незавершённой операцией. При опциональном nil repo поддержать существующие тестовые конфигурации.

Зафиксировать порядок locks: per-job operation/persistence mutex → кратковременный jobsMu. Запрещён обратный захват; jobsMu/timersMu не держатся при SQL/ожидании worker. Вызов callbacks из job не должен нарушать этот порядок. Для несвязанных задач не вводить один глобальный SQL mutex.

HTTP: 200 только после завершённой очистки; неизвестный ID — 404; удаляющаяся задача/timeout — 409 с машиночитаемым кодом; ошибки ФС/БД — 500. Не отдавать сырые внутренние пути/секреты. Контекстные ошибки различать; ответ клиенту, уже закрывшему соединение, не означает отмену tombstone. Старые обработчики/сигнатуры менять только после проверки всех вызовов.

## 7. Эксплуатационная приёмка Deezer

Скрипт `scripts/canary_verify_deezer.sh` вызывается внутри deployment-транзакции server2 и не владеет rollback. Любой его сбой возвращает ненулевой код владельцу транзакции. Он не запускается из go test.

Обязательны обе ссылки:

- `https://link.deezer.com/s/34V56T2tjsvcD5T8nYs3p`
- `https://link.deezer.com/s/34V58NTLPHDTQXR4unML6`

Для каждой:

1. POST /downloads/preflight; проверить 200, `.release.title`, `.release.artist`, непустой `.tracks`. Развёрнутый Deezer-ресурс должен пройти whitelist и проверки redirect.
2. POST /downloads с URL, `selected_track_indices:[0]` и новым проверяемым probe_deployment_id. Сразу проверить только непустой валидный `.id`; total_tracks пока может быть 0. Сохранить ID в серверном реестре текущего deployment.
3. Poll GET /downloads/{id} до WAITING_SOURCE. Предварительное разрешение — до 60 секунд, общий deadline всей ссылки — до 300 секунд; каждый curl ограничен отдельно. ERROR/CANCELLED/PARTIAL_READY и timeout — сбой. После метаданных проверить total_tracks=1 и получить настоящий `.tracks[0].track_id` через tracks API, не индекс массива вместо ID.
4. GET /api/downloads/candidates с URL-encoded artist/title/duration и version_policy=release. Проверить структуру и пригодность кандидата по evaluation, а не только наличие элемента. Передать POST /api/downloads/tracks/{TRACK_ID}/bind-source: `{"target_url":"<candidate URL>","version_policy":"release"}`. Никакого скрытого переключения на другую площадку после ошибки выбранного источника.
5. Дождаться READY, completed_tracks=1, total_tracks=1. Получить converted_path; проверить его принадлежность именно TMP_DIR/JOB_ID/converted, не доверять произвольному абсолютному пути из JSON.
6. Проверить MP3/44100 Hz/320000 bit/s аудиопотока через ffprobe. Для утверждения CBR дополнительно проверять bitrate заголовков MPEG-аудиокадров (с учётом padding); средний bit_rate сам по себе недостаточен.
7. Проверить ID3 major=4, revision=0, корректную структуру фреймов и UTF-8 текстовых фреймов; APIC должен реально декодироваться как attached_pic. Через GET /tags проверить `.tracks[0].title`, artist, album и соответствие preflight. Не принимать верхнеуровневый has_cover как доказательство встроенной обложки. Не допускать USLT/SYLT; multi-value и внешние lyrics покрываются также герметичными тестами.
8. Range bytes=0-1023 через /files/stream: 206, правильный Content-Range с общим размером, ровно 1024 байта и соответствие началу MP3. Это staging-путь, не перенос в MUSIC_DIR.
9. DELETE своей задачи: дождаться синхронного успеха; GET → 404, каталог отсутствует, ни один writer больше не существует. Ошибка очистки запрещает verified-квитанцию.

Pre-Sweep под тем же lock обрабатывает только зарегистрированные probe ID прежних deployment; неизвестные пользовательские задачи не трогает. Не полагаться только на trap: реестр атомарен и переживает аварийный выход. Окно «создали job, не успели записать ID» закрывается серверной меткой probe_deployment_id и поиском только по этой метке. Терминальные пользовательские задания и queued-задачи не очищать массово.

Живые источники могут быть недоступны из-за внешнего сбоя: это блокирует продвижение и приводит к предусмотренному rollback, но не доказывает дефект кода. В отчёте различать сбой площадки, контрактов, конвертации и очистки. Повторы ограничены и не ослабляют обязательность двух ссылок.

## 8. Качество, версии и герметичные проверки

Единая точка запуска — `scripts/lint.sh`, без установки инструментов из сети во время самой проверки. Версии инструментов хранятся в одном lock-файле; GitHub actions фиксируются commit SHA. Go берётся из go.mod; для текущего Go 1.26 golangci-lint должен поддерживать Go 1.26 (минимум v2.9.0) и быть собран подходящим Go. Схема .golangci.yml — v2 с отдельными formatters.

Нельзя считать старый goimports/govulncheck совместимым только потому, что его собрали новым Go: анализаторы/export data тоже требуют поддержки. Подобрать и зафиксировать точные совместимые версии всей цепочки при этапе 1, проверить на репозитории. Непроверенные старые номера v0.31.0/v1.1.4 из ранних редакций не являются утверждённым lock. Не использовать @latest/ubuntu-latest как обещание воспроизводимости: runner image и версии shell-инструментов фиксируются явно.

Проверки:

- gofmt/goimports без изменений; --fix отдельно и явно, с просмотром diff;
- govet, staticcheck, errcheck, ineffassign, unused, sqlclosecheck, rowserrcheck, bodyclose, noctx, errorlint, gosec, forbidigo; govulncheck отдельно;
- архитектурный запрет прямых файловых вызовов вне перечисленных низкоуровневых мест; исключения узкие. Forbidigo сам по себе не доказывает, что перед каждым safefs вызван Resolve;
- отсутствие запрещённых Docker/npm/runtime-артефактов и секретов в tracked-файлах;
- bash -n для **каждого** shell-файла в цикле (один `bash -n scripts/*.sh` не проверяет все), ShellCheck, shfmt;
- go test -v ./web/...; существующий regex-валидатор не объявлять полным HTML/Alpine/OpenAPI-анализатором. Новые проверки шаблонов/спецификации вводятся явно;
- полный `go test -v ./...`, `go test -race -p 1 ./...`, fuzz FuzzParseAPIC и FuzzDecodeText по 5 секунд с отдельным пакетом/паттерном. Timeouts выбирать по измерениям, с запасом для race, а не универсальные 60 секунд;
- внешняя сеть в тестах запрещена mock transport/контролем egress; loopback httptest разрешён. Контроль сети тестируется, а не только декларируется;
- обычная и статическая сборки, проверка SHA256 и git diff --check.

Zero Warnings вводится после инвентаризации и исправлений небольшими проверяемыми изменениями. Не выключать анализатор глобально ради зелёного CI и не выполнять массовую автоформатирующую правку поверх текущих незакоммиченных изменений других задач.

## 9. Проверки отказов и критерии приёмки

Go-тесты должны быть детерминированными: барьеры/каналы вместо ожиданий «500ms + 700ms». Обязательны pending timer и уже начавшийся callback, удерживаемый на барьере до DELETE.

| Группа | Обязательные сценарии |
|---|---|
| Worker lifecycle | delete одновременно с queue-start/retry/bind/release-switch/backfill; несколько исполнителей; cancel до регистрации; timeout и повторный delete; concurrent DELETE; release без двойного close; отсутствие повторного создания каталога |
| Persistence | pending timer, callback до/после tombstone, terminal SaveJob, сбой DELETE БД и повтор, nil repo; отсутствие восстановления записи после успешного удаления |
| HTTP | 200/404/409/500, отменённый контекст, unsafe job ID, отсутствие подавления ошибок |
| Queue | исходные true/false, загрузка persisted pause/hold до workers, probe при pause без запуска пользователя, пользовательское изменение паузы, hold другого владельца |
| Deploy phases | сбои preflight/backup/swap/restart/health/probe/cleanup/commit; rollback ровно один раз; ошибка rollback отдельна от rolled_back; падение до TX_ACTIVE восстанавливает hold |
| Signals/recovery | INT→130, TERM→143 до/после swap, повторный сигнал при rollback, SIGKILL/SSH disconnect + следующий recovery, недопущение следующего сервера после сбоя |
| SQLite/FS | WAL backup/integrity, rollback без восстановления DB, повреждённая DB оставляет service stopped; N-1 читает БД/задания N; несколько mount, нехватка места, пробелы/переводы строк, симлинки и неверный manifest |
| Retention | 5 succeeded + 2 незащищённых failed; карантин не вытесняет succeeded, текущий/last-good/recovery защищены; отсутствие ложного обещания фиксированного общего размера |
| Promotion | push/PR не меняют production; skipped needs; неправильный run/hash/ref, истёкший артефакт, fallback, смена canary, закреплённый SSH порт/ключ/host, stdout только JSON |
| Probe | обе Deezer-ссылки, deferred total_tracks, настоящие track ID, valid target_url, ошибки площадок, ID3/APIC/CBR/Range, аварийный выход до записи ID, очистка только собственных job |

Shell mock-тесты подменяют ssh/scp/systemctl/curl/sqlite3 и используют только временные каталоги проекта. Они не обращаются к серверам и не останавливают локальные сервисы.

## 10. Порядок реализации

1. Зафиксировать этот план, описать новые API/capabilities и согласованную оговорку эксплуатационной сети в AGENTS.md. Инвентаризировать текущие изменения и интерфейсы; не перетирать чужую работу.
2. Выбрать совместимые точные версии инструментов, добавить lint.sh и v2-конфигурацию, получить baseline без предупреждений. На этом шаге не включать автоматический деплой.
3. Реализовать и проверить worker lifecycle, синхронный delete, callbacks/persistence, HTTP-ошибки. Legacy менять только при необходимости, с компиляцией всех потребителей.
4. Реализовать persisted pause/hold/probe и совместимость N/N-1; подготовить безопасный baseline rollout. Пока его нет, capabilities preflight блокирует новый автоматический конвейер.
5. Переработать deploy.sh: target config/SSH, lock/journal, backup, атомарный swap, health, EXIT/signals, rollback и queue cleanup. Пройти весь mock fault-injection набор.
6. Добавить probe, registry/Pre-Sweep, квитанцию, read/fetch-подкоманды и ротацию. Проверить исключительно mock/fixture-контуром до явного canary rollout.
7. Включить workflow с маршрутизацией из §2.1 и неизменяемым артефактом. Перед включением проверить secrets, known_hosts и минимальные permissions.
8. Отдельно авторизованный canary-выпуск: обе живые ссылки, очистка, отчёт, hash, восстановление состояния. Production только отдельным ручным продвижением.

Готовность реализации: все перечисленные проверки зелёные, оба сервера используют собственные фактические настройки, rollback проверен, рабочая документация/PROGRESS.md отражают фактическое состояние. Наличие этого плана не означает готовность реализации или успешный деплой.
